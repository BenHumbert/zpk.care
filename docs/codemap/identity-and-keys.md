## Open questions
- OQ-A. `processMigration` dereferences `tokenRecord.localData` (`enrollment-service.ts:572-585`) but `TokenRecord` has no such field and `generateToken` discards `localData` (`token-authority.ts:31-52,151-159`); is the migration path expected to be dead, or is `TokenRecord` extended elsewhere?
- OQ-B. Is `/onboarding/generate-key` meant to keep accepting an attacker-chosen `enrollmentKey` in the request body (`member-routes.ts:141-142`) outside tests?
- OQ-C. Which process is supposed to pin the sequencer's attestation public key? `verifyAttestation` trusts `att.pk` (`nfc-attestation.ts:258-270`) and the engine's key is derived from a hard-coded seed (`interactive-service.ts:511-513`), while `L2Node` uses the gossip secret (`start-leviathan.ts:288`), so two different signing keys exist in the same process.
- OQ-D. The member node sends its six preimage Fields (incl. hash(enrollmentKey)) to the sequencer so the engine can run ProofGate/StateTransition on the member's behalf (`member-routes.ts:558-565`, `interactive-service.ts:1601,1608-1613`). Is that the intended production trust model or fixture-only scaffolding?
- OQ-E. `proverUrl` is read by the Nautilus starters (`start-member-nautilus.ts:85`) but no code constructs `ProofDelegateClient`; is the :4040 delegate meant to be wired, and does its API key (`proof-delegate.ts:279-281`) count as caller authentication for preimage-bearing requests?
- OQ-F. `recoverFromCard` requires the raw identity fields again (`wallet-migration-service.ts:114,129`); where would they come from on a new device, given the card stores only hashes?
