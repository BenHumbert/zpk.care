# A voiced, four-window walkthrough of one claim

Feasibility and design of 2026-10-19 for the owner, modelled on the SwapStreet bidding demo (Z:ByteStreetCustomBeta
ft-swap-platform	estnetsite-e2edemo-bid.mjs). Three agents: one studied the SwapStreet demo, one inventoried zpk screens and live data, one designed the walkthrough. Nothing is built.

## Verdict

Yes, with work: every step from plan to dispense already has a real dashboard screen or a server call the harness exercises, and the SwapStreet tooling carries over, but five steps have no screen, the math screen needs a device-side feed that does not exist, and like SwapStreet the result is a recorded take of real actions put together afterwards, not a live broadcast.

## How the SwapStreet demo works

Found it. The demo lives in Z:\ByteStreetCustomBeta. The script is Z:\ByteStreetCustomBeta\nft-swap-platform\testnet\site-e2e\demo-bid.mjs (660 lines). Its helpers are in the lib folder next to it: stage.mjs, narrate.mjs, board.mjs, bid-script.mjs, metamask.mjs, site.mjs and bid-prep.mjs. Each take is written to Z:\ByteStreetCustomBeta\demo\<timestamp>-bid. The latest full take is Z:\ByteStreetCustomBeta\demo\2026-10-13T15-56-35-bid\grid.mp4. It is not a live multi-window screen. It is a scripted recording that is put together afterwards.

How it works. One Node process uses Playwright 1.63.0 to run three headless Chromium browsers. Each browser has its own real MetaMask 13.50.0 profile: Maya the seller, Dev the buyer and Nina the bidder. A fourth headless page is the "board". There are no real people at the controls. Each person's part is an async function (makerFlow, takerFlow, bidderFlow). All three run at once with Promise.all, and shared promises (listingD, devSpottedD, ninaOfferD, devOfferD, executedD) hold each person back until the event their story needs has happened. Every transaction is real and goes to Sepolia.

The on-screen layer. stage.mjs adds a big cursor that moves on an eased curve, click ripples, a caption bar and a name badge. It also changes Playwright's click, fill and selectOption so that each one first glides the cursor to the element and types one letter at a time. MetaMask's own confirm screens are copied into the site window as a floating panel, using a Chrome DevTools screencast (mirrorPrompts in metamask.mjs). The cursor then glides onto MetaMask's real button.

The board. It is a static HTML page with no data source of its own. The script pushes updates into it with page.evaluate: setListing, upsertOffer and addTx. A watcher checks each browser's wallet log every 1.5 s, waits until each transaction is mined, and then adds it to the board.

Voices. They are local, free, AI text-to-speech. Kokoro, Chatterbox and Chatterbox Turbo run on the CPU. Maya1 and Orpheus run on the GPU through llama.cpp Vulkan. Piper is also supported. Each engine runs as a Python worker that loads its model once and handles one JSON request per line. narrate.mjs passes a "talking stick" so only one person speaks at a time. Each person waits for their line to finish before they act. Lines are cached as WAV files and checked with faster-whisper before a take (voice-check.mjs). The final cast is Maya on maya:seller, Dev on turbo:am_puck and Nina on maya:rival.

Assembly. Every page records itself to webm through Playwright. When the scene ends, the full ffmpeg 9.0.2 build cuts each video to a shared start time (T0), lays down a mixed voice track, and stacks the four videos into a 1920x1080 grid with xstack. The script also writes narration.srt, transactions.md, .csv and .json, and a player.html that shows grid.mp4 and highlights each transaction row as the video plays.

Length. The final take runs about 10:40 by its captions (the notes say 11 min) and has 15 transactions, all successful. The earlier final take, 09-11-20-bid, runs about 13:13 to 13:33. Rehearsals ran 1:37 to 8:03. A 2x copy is 5:30. The script stops the scene if it passes 30 minutes.

proof.html and grid-2x.mp4 were not made by any script in the repo. The saved project notes say proof.html is a copy of a private claude.ai artifact, and the 2x copy was a one-off ffmpeg command using atempo.

For zpk.care: the same design carries over. It would take a different cast (for example member phone, pharmacy, insurer), a different set of story lines, and a board page fed by the harness with hashes, proofs and roots instead of transactions.

Reusable:
- lib/stage.mjs (217 lines): no SwapStreet code in it. It works with any Playwright page: big cursor, eased glide, ripples, caption bar, name badge, and slowed click, fill and selectOption. It can be copied as is. Z:\ByteStreetCustomBeta\nft-swap-platform\testnet\site-e2e\lib\stage.mjs
- lib/narrate.mjs (392 lines): text-to-speech wrapper with several engines, cache, mood, cue handling, talking stick (Narrator.say), mixTrack (lines placed in one WAV by time), srt captions and an ffmpeg runner. Only toSpeech() holds SwapStreet words (tickers, PSA). It needs the external Z:\ByteStreetCustomBeta\.tools folder (piper, ffmpeg, the tts venvs and models), or SWAPSTREET_TOOLS pointed elsewhere.
- Z:\ByteStreetCustomBeta\.tools\tts\worker_*.py and llama_snac.py: Python workers that keep a model loaded and answer one JSON line per request (Kokoro, Chatterbox, Turbo, Maya1, Orpheus), plus check_asr.py (faster-whisper check).
- lib/board.mjs (110 lines): the fourth-panel pattern. A self-contained HTML page in its own recorded headless Chromium, updated only by the harness through window.board.<fn>(arg). For zpk.care this would become a 'calculations and hashes' panel (wallet ID Poseidon hash, Merkle roots, proof generated and verified, what each party receives) with the same update(fn, arg) API.
- lib/bid-script.mjs structure: a cast object with every number, storyLines(cast) giving {text, mood} per beat per person, and PROMPT_LINES looked up as stage:kind:asset. This keeps the words separate from the choreography.
- Choreography pattern in demo-bid.mjs: one async flow per person, run with Promise.all, coordinated by deferred promises and an until() poller, with a shared fail() that rejects every deferred, plus a watchdog.
- The ffmpeg steps in demo-bid.mjs lines 576-594: cut each webm to a shared T0 using each page's videoStartedAt, mux a per-person voice WAV, encode with loudnorm, then 4-way xstack into a 1920x1080 grid.
- The player.html generator in demo-bid.mjs lines 642-655: a video with an event table that highlights rows on timeupdate and seeks on click. For zpk.care the rows could be claim steps with their hashes.
- voice-audition.mjs and voice-check.mjs: compare voices side by side and check every line with Whisper before recording.
- lib/metamask.mjs mirrorPrompts (lines 1579-1733): streams a second browser window into the main page with CDP screencast and maps button points into it. Only needed if a separate wallet or phone window should appear inside another window's recording.

## What zpk has to build on

Most of the claim can already be done by clicking in the real dashboards. The harness (scripts/e2e-verify/run.ts) shows the exact calls for every step. These steps are clickable today: the insurer plan, the marketplace signup and the insurer's approval of it, the employer group, the HR Tool codes, member onboarding (code, salted wallet derivation, recovery PIN, registration proof), the PCP pick, prescribing (claim 1 of the last harness run went through the prescriber dashboard and completed), and fill, verify, dispense and payment at the pharmacy. Five steps run with no click and no UI: the insurer's approval of the wallet (server to server), the engine opening the member record, the phone's credential-mint proof, the phone's claim-update proofs (a 20 s background loop) and batching. Two things are not wired: recovery from a card in the member UI, and an operator-token box in the explorer. Since D1/D2 the explorer cannot show member claims, receipts or event streams.

For the fourth screen, the richest live source is the open engine console stream, GET :3030/interactive/console. It prints proof steps, timings, public inputs and outputs (prescription hash, forest roots, entry commitment, patient and plan pay, deductible credit, NDC hash), accumulator before and after, and Merkle leaf positions. The values are truncated and come as text. Viz events carry names and amounts but almost no hashes. On the live path they cover prescribing and the fill only; the enrollment viz events fire only on the legacy fixture path. The chain SSE carries receipts, wallet IDs, batch roots and settlement. Nothing reports what the device computes (salt, the six field hashes, the wallet Poseidon, the ownership proof, wallet-update roots). A new demo-only device feed is needed for that.

The legacy visualizer is not served by the launcher and is broken against the current topology. zpk_care has no browser automation and no TTS. The SwapStreet Arcade folder has a Playwright multi-browser bot runner. The swapstreet v6 bidding walkthrough itself was not found on Z:.

Security for the demo: the console stream and /viz/history are still open. The console prints display names beside wallet ID prefixes, so a demo should not build on that staying open. Every other stream and member read needs the operator token (passed as ?token= in the EventSource URL, so keep devtools off screen). Member fixtures and harness people are fictional. The provider fixtures were real Madison, WI doctors and pharmacies from NPPES, and the :4002 and :4003 nodes ran as two of them. Fictional providers have since replaced them in place. Boot every take from genesis so that no old provider rows survive in saved state. Raw identity fields, salts, preimage hashes, the enrollment key, card shares, PINs and tokens must never appear on the math screen as shared.

Gaps:
- The trace on disk predates D1, D2, D4, D5 and B8. The current single-member run was still underway, so today's pass or fail per step is not confirmed here.
- Not verified: whether the provider onboarding wizards and insurer credentialing approval work end to end. The default boot pre-seeds providers and the harness never clicks through them.
- Not verified: whether pharmacy /nfc/scan with a pasted attestation works today. The harness dispenses without scanning.
- Recovery from a card cannot be clicked. The member Restore screen uses the old PBKDF2 format and does not call /onboarding/recover.
- The phone's proofs (credential mint, PCP update, claim updates) run in a 20 s background loop with no button and no on-screen result in dashboard-member.
- The insurer's approval of the wallet and the engine's member record have no UI and no viz event, only console lines.
- The explorer has no operator-token input, so its member views and streams are blank since D1/D2.
- No device-side event feed exists for the salt, the six field hashes, the wallet Poseidon, the ownership proof or wallet-update roots. It would need a demo-only, localhost-only, credentialed feed that never ships in production.
- Live-path viz events carry no hashes or public outputs. Those exist only as truncated console text or in route responses.
- Before the console stream is relied on, it should be gated: it is open and prints display names beside wallet ID prefixes. /viz/history is also still open.
- The provider fixtures were real NPPES doctors and pharmacies until fictional rows replaced them in place. Plan networks saved before the swap must be rebuilt, because provider wallet IDs derive from the NPI.
- The 'PLAN-GOLD-2026' label is hard-coded in the eligibility console and viz output, and the console says '10 Fields' though the output has 12.
- Pacing: registration took about 941 s in the last run, prescribing about 30-40 s and filling about 15-40 s. Real time needs cuts, pre-warmed state or a time-lapse.
- The pharmacy UI takes the drug cost from the claim and defaults the fee to 1300, so it cannot reproduce the harness's three deductible scenarios without new inputs.
- The HR Tool imports a CSV only from a file. A driver must supply the file.
- No browser automation or TTS in zpk_care. The swapstreet v6 bidding walkthrough the owner mentioned was not found on Z:, so its exact tooling is unknown.
- Secrets the harness prints (enrollment key, salt, preimage fields, card shares, PINs, tokens) must stay off any public recording unless the owner decides otherwise. The operator token rides in ?token= on EventSource URLs.

## The design

**Windows.**
- Grid: four tiles. Record each tile at 1280x720 and stack them into a 2560x1440 grid. At SwapStreet's 960x540 tiles, dashboard text is too small to read. A 1920x1080 copy can be scaled down from the larger grid. Layout: W1 top left, W2 top right, W3 bottom left, W4 bottom right.
- W1, Avery's phone (one role all the way through). Page: dashboard-member at :4001. Use a fictional member: the harness's Avery Quillfeather (scripts/e2e-verify/run.ts:120-124). Steps: unlock with the device PIN, type the enrollment code and the SMS PIN, type identity fields and consent, derive the wallet. The page shows only 'Wallet derived: <short hash>' (dashboard-member/app.js:588-640). Then the recovery PIN and two cards, compile and prove registration (app.js:645-690), and pick the PCP (app.js:1298). At pickup, request the attestation (app.js:1454-1562). The phone's background proofs have no indicator in the page. An overlay driven by the new device feed shows them instead: 'Your phone is proving the claim update, 0:18'. First check how dashboard-member looks at phone width. If it does not fit, record it in portrait and scale it into the tile with a phone frame. Use the spare width for a fixed 'stays on this phone' list: name, date of birth, salt, enrollment key.
- W2, the plan side (changes roles). Act 1: the insurer analyst publishes the plan in dashboard-insurer at :4004, with the formulary and network boxes ticked (dashboard-insurer/app.js:850-1054). Act 2: the employer owner applies at :4004/marketplace/ (Ed25519 key made in the browser, sample CP 575 PDF, sign, activate, collect credentials with the activation code). W2 switches to the insurer, who approves the application. It switches back to the employer, who creates the group in dashboard-employer. That page is on an ephemeral port, which the director reads from the activation credentials (run.ts:279-307). Then the HR person uses the HR Tool on :5050 (dashboard-hr-tool, CSV import, codes and PINs shown once). Act 3: W2 is the insurer again. A toast fed by the new approval event shows the wallet approval, which has no screen today (src/nodes/routes/insurer-routes.ts:447-540). Act 5: W2 becomes the Leviathan dashboard at :3030 and shows the batch being built and settled. Each switch is a page.goto in the same recorded page, so the tile stays one continuous video. A 2-second title card names the new person and gives them a new name badge.
- W3, the care team (changes roles). Acts 1 to 3: the Leviathan dashboard at :3030 shows receipts arriving as the 'network' view. Set the operator token off camera before T0 with page.evaluate(RPC.setAdminToken). Never type it on screen (dashboard-leviathan/rpc.js:36, 236). Act 4: a fictional doctor writes the prescription in dashboard-prescriber at :4002. Pick the patient (it shows as 'Member' or a short hash), the pharmacy and the drug, then click Write Rx (rx-patient-select, rx-pharmacy-select, rx-med-select, rx-write-btn; dashboard-prescriber/app.js:376-500). W3 then switches to a fictional pharmacist in dashboard-pharmacy at :4003: Fill, Verify Member with the pasted attestation, 'Dispense (Collect Payment + Settle)', then 'Payment Received' (dashboard-pharmacy/app.js:527-542, 811, 1141-1151).
- W4, the math screen (one role). It is a self-contained board page in the director's own recorded Chromium, on the lib/board.mjs pattern. It has no network access and holds no tokens. The director updates it with page.evaluate. It shows one card per calculation, a step counter with a proof timer, and a 'who knows what' grid that fills in as data moves. During every proof wait longer than about 8 s, W4 becomes the focus: a narrator explains the circuit while the proof runs.
- Story (22 steps, 5 acts). 1: insurer publishes the plan. 2-4: employer applies, insurer approves, employer signs and activates. 5: employer creates the group. 6: HR issues codes. 7-9: phone unlocks, redeems the code, derives the wallet. 10: insurer approves the wallet (no click). 11: recovery cards. 12: compile and prove registration. 13: engine opens the record and the phone proves the credential mint. 14: PCP pick and its proof. 15: prescribe (four engine proofs, about 37 s, from e2e-out/trace.json step 17). 16: pharmacy fills. 17: phone attestation, pharmacy verifies. 18: dispense and adjudicate (17 to 28 s, e2e-out/results.json proofTimesMs). 19: phone proves the claim update. 20: payment received. 21: batch built and settled. 22: closing 'who knows what' summary. Leave recovery-from-card out of version 1. It cannot be clicked today.

**Driving the clicks and typing.** Use Playwright 1.63.0. It is the version in Z:\ByteStreetCustomBeta\nft-swap-platform\node_modules\playwright, installed 2026-10-05, so it is more than two weeks old. It is also the version stage.mjs ran with for the Oct 13 take. Do not use 1.64.0 (SwapStreet Arcade). It was installed on Oct 13, less than two weeks ago. zpk_care has no browser automation today (Z:\zpk_care\package.json), so add playwright@1.63.0 as a dev dependency. Or keep the demo in its own folder with its own package.json and resolve o1js from the root. Node is v22.21.0.

Shape. Write one Node ESM director, for example scripts/demo/claim-walkthrough/director.mjs (not created). It uses one Chromium with four contexts, each with recordVideo at 1280x720. MetaMask is not needed, so the extension and persistent-profile work in metamask.mjs drops out. Boot the network with ZKTRIDENT_OPEN_BROWSERS=0 so the director opens its own windows (src/nodes/start-leviathan.ts:782-870). The director starts the HR Tool itself (npm run start:hr-tool, or the harness's startHrTool, run.ts:317-323), because the launcher does not.

Steps as data. Each step is a record: {n, window, actor, caption, lines, act, waitFor, math}. This follows SwapStreet's cast plus storyLines split (lib/bid-script.mjs). The step titles and check names in scripts/e2e-verify/run.ts (the trace.begin titles at lines 230-966) give the captions. This story is mostly sequential, unlike the three-way bidding race. So run the steps as a simple ordered loop and keep Promise.all only for the cut-aways. Keep SwapStreet's deferred promises keyed by event, the shared fail() that rejects them all, and a watchdog. Set the watchdog to about 60 min, not 30.

Clicking and typing. Copy stage.mjs as it is. It gives the large cursor, the eased glide, ripples, the caption bar, the name badge, and character-by-character fill at 85 to 155 ms per key. Use the stable IDs: ob-pin, ob-token, ob-enroll-pin, ob-cid, ob-fn, ob-ln, ob-dob, ob-recovery-pin, rx-*, csv-file-input, admin-token-input. Find generated buttons by role and text: Fill, Verify Member, 'Dispense (Collect Payment + Settle)', Set PCP, Payment Received. The HR import needs setInputFiles with a CSV the director writes. The stage can animate a drag over the drop zone first. Never reload the marketplace page, because a refresh makes a new Ed25519 key (dashboard-marketplace/app.js:398-416).

Handoffs between windows are simulated, and the captions say so. The director reads the code and PIN from the HR Tool page and types them on the phone, with the caption 'code by email, PIN by SMS'. It reads the attestation JSON from the phone and pastes it into the pharmacy box (dashboard-pharmacy/app.js:1021), with the caption 'shown at the counter'.

Waiting for the network. There are three kinds of wait, all with long timeouts. (1) The DOM: locator.waitFor up to 180 s for result text. (2) Polls run by the director, as in the harness: member /onboarding/status phase, pharmacy /dispensing/fill-status?jobKey, and l2_getReceiptsByWallet (run.ts:394-428, 615-640). (3) Chain SSE events held in Node with the operator token in a header, never in a page URL: proof:accepted for the wallet, batch:built, batch:settled. Trigger the batch with the admin-gated /interactive/force-batch. Do not use the Leviathan Quick Setup wizard. It calls l2_forceBatch without the admin flag (docs/codemap/dashboards-and-tools.md:147-151).

Proof pacing. Device proofs take 25 to 45 s (scripts/dev/README.md:41-43). Engine prescribing takes about 37 s. A fill takes 17 to 28 s. The phone compile took about 27 s. The last trace on disk shows registration at 941 s (e2e-out/results.json:131), but that run predates the D7 proving lease, so measure again. Keep one proof running at a time. Wait for the phone's 20 s background loop to show pending 0 before the next engine action. All proofs share the one CPU, and a device proof that overlaps a ledger change gets invalidated (A-33).

Keeping it watchable. Each line is spoken before its action, using the talking stick, so actions follow the speech. During any wait longer than 8 s, start a cut-away: W4 highlights the circuit being proved, a narrator line explains it in under 25 s, and the board header shows 'Step 12 of 22, Avery's phone, proving registration, 0:23 of about 0:35'. If the proof outlasts the explanation, the director writes the interval to cuts.json, and post speeds it up 4x to 8x with a visible 'sped up' badge. Add a --rehearsal flag that turns off typing delays and voices, and a --stop-after n flag.

**Voices.** Recommendation: reuse SwapStreet's local voices first. Hosted voices are an option for a final take.

Local. narrate.mjs wraps Kokoro-82M (Apache-2.0, CPU), Chatterbox and Chatterbox Turbo (MIT, voices made from reference clips), Maya1 and Orpheus 3B (Apache-2.0, GPU through llama.cpp Vulkan) and Piper. Each engine runs as a long-lived Python worker under Z:\ByteStreetCustomBeta\.tools\tts, and SWAPSTREET_TOOLS points to that folder. Cost is $0. The tools are installed and proven, and voice-check.mjs checks every line with faster-whisper.

Hosted. ElevenLabs has the strongest stock and designed voices. It is priced per character on monthly credit plans, and commercial use needs a paid plan. OpenAI TTS (tts-1 or tts-1-hd, gpt-4o-mini-tts) is priced per character or per minute. This script is about 2,000 to 2,500 words, about 15,000 characters. A full cast render would cost well under a few dollars on OpenAI TTS and would fit inside an entry ElevenLabs month. Every re-render costs again. My prices date from before mid-2026, so check the current price pages. Sending the script to a vendor is fine here: it holds only fictional people and no live values.

Cast, one voice per role. Avery, the member. Jordan, the employer owner and HR person, one person at a small firm. An insurer analyst. A fictional doctor. A fictional pharmacist. A narrator for the math screen. Roles that share a window get clearly different voices, so the viewer hears the change. Use stock or designed voices only, never a clone of a real person.

Script. Write about 120 to 150 lines: 3 to 6 per step plus the cut-away explanations. Use plain words and the first person for each role, for example 'I type the code from HR's letter. The phone never sends my name.' The narrator explains: 'The phone hashes each field with a salt only it holds, then hashes those together. Only the result leaves the phone.' Never speak hashes or values that change per run. Amounts follow from the plan, so they can be spoken safely. This keeps every line static, so all of them can be rendered and checked with Whisper before the take. That matters here, unlike SwapStreet: the CPU must stay free for o1js proofs during the take, and the cache by SHA-1 (narrate.mjs) means nothing is synthesised live. Rewrite toSpeech() for zpk terms: NDC as 'N D C', PCP as 'P C P', Poseidon, dollar amounts from cents, wallet as 'wallet I D'.

Sync. Keep SwapStreet's method. Narrator.say shows the caption on that role's page, waits for the clip length plus 350 ms, and records the start time. mixTrack places each clip at its time, one track per window. srt() writes captions. Cut-away narration goes on the W4 track. Disclosure on the board: 'Voices are AI-generated. The people, employer, doctor and pharmacy are fictional. Every proof is real.'

**The math screen.** Host: a static board page in its own recorded Chromium, with an update(fn, arg) API on the lib/board.mjs pattern. The director feeds it. The page never calls the network, so no token and no CORS question touches it. A live variant could later be served from explorer/ on :8000, which is already in the CORS allowlist (src/security/network-policy.ts:47).

Feeds, all read by the director in Node.
(a) Playwright page.on('response') on W1 to W3. It reads only the response JSON of an allowlist of paths and fields, and never request bodies, because the derive-wallet request carries the identity fields. Paths: /onboarding/derive-wallet (walletId), /prescriptions/prescribe (rxHash, prescriptionCredential.forestRoot, proof times), /dispensing/fill-status (adjudication, accumulator before/after/limits, fulfillmentDetail with its 7 fields and commitment, settlementCommitment, walletUpdate.newInventoryRoot, l2Receipt.receiptId, proofTimesMs; run.ts:625-690), the marketplace agreement and sign responses, and the HR import (employeeIdHash).
(b) Chain SSE /events with the operator token in a header: proof:accepted {receiptId, walletId, sequenceNumber}, batch:built {batchNumber, old/new registry root, proveTimeMs}, batch:settled (l2-final-N), audit:event (src/l2/l2-node.ts:146-186, 1312-1325). Also /viz/events for the prescribing and fill events (interactive-service.ts:2571-2940, 3097-3674).
(c) Gated reads by the director: l2_getWalletState for credentialInventoryRoot, the claim witness for the leaf and its Merkle path, the audit log, and /interactive/state for the member record.
(d) The new demo-only device feed and engine events listed under events_to_add.
(e) Values the director recomputes with o1js Poseidon. Each card gets a 'recomputed here: match' tick, which turns the screen from display into verification.
(f) Optional, and only after it is gated: /interactive/console as a scrolling proof log. Do not build on it while it is open.

Each card shows: the step number, where the work happens (phone, engine, sequencer, insurer, employer machine), the formula in monospace with named inputs, the inputs that may be shown (public values, shortened like 0x1a2b...9f3e), locked chips for the inputs that may not ('name: stays on phone'), the output, and arrows lit toward the parties who receive it, with struck-out arrows for parties who never do ('Employer: never sees the wallet ID').

Cards.

Wallet: h(x) = Poseidon(hashString(salt), x) for cardholderId, dob, first, last and enrollmentKey. walletId = Poseidon(0, h(cid), h(dob), h(first), h(last), h(key), hashString(groupId)) (src/zkp/hash-utils.ts:113-126). 10. Prescription: four proofs with times, rxHash, prescription forest root, eligibility and formulary checks.

**Risks.**
- CPU contention. The engine, the phone, four Playwright video encoders and any TTS all share one CPU. Proofs can slow down or overlap, and a device proof that overlaps a ledger change is invalidated (the A-33 behaviour the D7 lease only partly covers). Mitigations: render all voices before the take, keep one proof running at a time, record at modest settings, and expect some takes to fail.
- Long, fragile takes. Every proof is real, so a raw take runs 25 to 35 minutes, and any failure means a genesis reboot plus the full take again. There is no tested mid-story checkpoint.
- The demo feed is new code next to the secrets. If it ever ships enabled, or emits a field hash or salt, it breaks rules I1 and I2. Keep it behind a flag, on localhost, behind a credential, and under a test.
- The response sniffer can see request bodies that carry identity fields. It must read only allowlisted response fields and must never log request bodies or full exchanges. The harness trace does log full bodies, so it cannot be reused for this as it is.
- Legibility. The dashboards were not designed for a quarter of the screen. Even at 1280x720 tiles some text will be small. The math screen must be designed for its tile size from the start.
- Selector drift. Hardening is still in progress (B3 and B7 wait on decisions), and the naming refactor will rename things. Dashboard changes will break selectors, so keep a rehearsal run in the loop and build after those items settle where possible.
- Honesty. Sped-up waits, the simulated SMS and email delivery of codes, and the simulated counter scan must be labelled on screen. 'Payment Received' is not settlement. Recovery and messaging are left out, not shown working.
- Data on screen. Provider names go out through the console, viz events and fixtures.json. They were real until the fictional dataset replaced them, and state saved before the swap still holds the real ones, so every take boots from genesis. Identity typed on W1 is acceptable only because the person is fictional. Tokens must be throwaway values for each boot.
- Tool coupling. stage.mjs patches Playwright's Locator click, fill and selectOption, so pin 1.63.0. narrate.mjs depends on the external Z:\ByteStreetCustomBeta\.tools folder, and there is no README for how it was installed. Copying it across machines is undocumented work.
- Voice quality and cost. Local voices vary from line to line, so the Whisper check helps but listening is still needed. Hosted voices cost money again on every re-render, and prices may have changed since my data.
