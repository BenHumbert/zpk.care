# The engine: what it is, where it should run, and provider keys without hardware

Review of 2026-10-18 for the owner. Four agents: a map of the engine today, an analysis of moving it into its own process, research on provider keys that need no hardware purchase, and a skeptic who checked the engine claims against the code (55 of 67 confirmed; corrections are listed below and override the claims they correct). Nothing here is built.

## What the engine is

In this repo, "the engine" means the adjudication service: one class, AdjudicationService, plus its web routes and a small pool of helper processes that make proofs. It knows the plan rules and the drug list, checks each prescription and fill against them, works out who pays what, and keeps the working records of members, prescriptions, fills and prior authorizations. Today it runs inside the Leviathan sequencer process. It is built there at boot, answers on the sequencer's own port (3030), and can read and change the ledger's trees directly. Since B1 and B2 it holds no member identity, and the member's phone proves every change to its own wallet. It still holds the demo prescribers' and pharmacies' keys and makes their proofs for them, and it still decides the claim amounts the ledger records without any proof the ledger checks.

## What is risky or confusing about it today

- The word is overloaded. In this repo the engine is AdjudicationService plus its routes and proof pool. src/engine/ holds StateTransitionProgram and a dead CareContract (CODEMAP:58). visualizer/engine/ holds console drivers (CODEMAP:68). The routes are named /interactive/*, the logs say [interactive], and the plan calls it the plan's service. A reader cannot tell these apart without the code map.
- It lives inside the ledger node. Every Leviathan that boots also boots its own engine with its own state file. With three nodes there would be three engines with separate records, and a script priced on one node could not be filled through another. Its compile forced the verifier into a child process, a pool failure blocks the sequencer, and the network's software identity comes from it.
- It can change the ledger without proof. adminMutate registers wallets and sets lifecycle with no proof. Before B4's code is written, it also provisions every seed provider at each boot. A1 made submitted proofs trustworthy, but these writes skip that gate.
- It writes the money without proof. The fill proof is made and dropped. The amounts the ledger records come from the engine's commitPendingClaim, and the phone signs a root without seeing the proof or the totals. So no one outside the engine can check a charge. This is A-22, still open.
- A money defect hides under this. After the first fill, reversal or rollover, the engine resets the member's limits to $500, $8,000 and no benefit cap. A member on a $6,000 OOP plan is capped at $8,000 afterwards. Nothing compares the proof's new root with the root the phone is asked to prove. The single-member harness expects the fixed limits, so it passes.
- Plan binding looks incomplete. By static reading, every phone member's eligibility credential names PLAN-GOLD-2026 and ACME-CORP with a $30 copay, and the fill copay comes from the engine's own formulary tiers. The approved plan's copay and the insurer's formulary overlay are never used in pricing. AUDIT A-9 is marked fixed; this reading was not run live.
- Pricing does not match the owner's decision yet. Nothing is priced at prescribing; the patient's share appears at dispense. Ingredient cost is AWP (NADAC times 1.2) or whatever the pharmacy sends, and the circuit does not bind the price to any list. The owner chose NADAC plus a dispensing fee, priced before the script is written.
- The engine still acts as the providers. It holds every seed prescriber's and pharmacy's identity preimage and proves as them, so only the 31 seed providers can prescribe or fill. A real credentialed provider cannot take part until provider keys leave the engine. The fill circuit takes the pharmacy's identity as a private input, so once the engine holds no keys the fill proof has to be split.
- The routes do not know who is calling. Any pharmacy-role key can fill or reverse any pharmacy's script. Through prescribe-and-fill it can also write a script in a seed prescriber's name, and that passes B5 when the prescriber happens to be the member's PCP. Any prescriber-role key can name any seed prescriber index.
- Throughput is one engine operation at a time per node. A fill makes three proofs under the node-wide proving lock, then forces a batch.
- State at rest is plain JSON on one machine. It links wallet IDs to drugs, display names and plan approvals. D6 (encryption at rest) is not done, and there is no backup or replica of this file.
- Smaller confusing items: chart events probably dropped, a formulary publish route that stores nothing, a launcher comment that says no seed data while the engine seeds providers, and a lookup method that rewrites every member's working credential.
- Benefits of putting the engine at the front of the flow, at prescribing. The member and prescriber see the price while the script is being written. Refusals (PA, step therapy, network, consent, terminated member) happen before the script leaves the office; the code already runs those checks at prescribing (interactive-service.ts:2475-2556). Each script is adjudicated once, and the pharmacy only verifies and collects. The engine already holds the formulary and plan rules, so no pharmacy has to learn the family's spending. What is missing is the price itself: today it is computed at dispense.

## Defects the skeptic found that both reports missed

- Today the 'phone' signs with no person in the loop. It is the member node process (start-member-nautilus.ts), which holds the preimage and proves every queued update on a 20-second timer (start-member-nautilus.ts:123-129; member-routes.ts:97-185). The owner's rule is that the phone checks the claim before signing. That needs a review-and-approve step, plus a payload that carries the proof and the old and new totals.
- Dates in the proofs are constants. Scripts are written on 20260201 and expire 20270201. Eligibility is checked as of 20260202, the formulary check uses 20260101, and termination defaults to 20260214 (interactive-service.ts:2599-2600, 2673, 2706, 4475). The eligibility circuit checks the date range against that constant (eligibility-program.ts:141-148). Once proofs are kept and verified, they must use the real date.
- A prescriber can overwrite an existing prescription. The prescribe route passes a caller-supplied rxId (interactive-routes.ts:604). createPrescription stores it with no duplicate check (interactive-service.ts:2558, 2837-2861), which resets the quantity dispensed and the refills used. A prescriber-role key could reuse a filled script's ID.
- The engine writes the sequencer's audit chain directly, with no proof. Every prescription and message adds a messaging audit event (interactive-service.ts:2814, 4009, 4191; l2-node.ts:659-668). The move must also turn this unproven ledger write into a signed method.
- Replicas take admin roots on trust. Each adminMutate gossips only the new roots, and a replica applies them with no leaf data and no check (l2-sequencer-service.ts:1486-1490, 1540-1545; l2-node.ts:438, 1010-1014). A replica's trees then disagree with its roots. Typed admin records are needed for E7 as well as E3.
- Proofs bind to the engine's own formulary tree: a 100-drug Merkle tree that grows on demand. They do not bind to the sequencer's FormularyService or the insurer's overlay, and the engine never reads either (no formulary-service call in interactive-service.ts; tree built at 754-845, grown at 950-998). Before pricing can come from the sequencer's NADAC list, the proofs have to bind to that list's root.
- Production must require ZKTRIDENT_TRANSITION_VK_HASH. Without it the sequencer still runs, using whatever verification key it compiled (start-leviathan.ts:245-261). The claim-proof verifier the owner wants will need its own pinned key, also required.
- A quote while the script is being written cannot reuse today's prescribe route. That route makes four or five proofs, all thrown away, in about 35 seconds under the node-wide lock (interactive-routes.ts:136-138, 597). The quote needs a pricing path with no proofs and no lock.
- The proving lock can be freed while work is still running. The 5-minute timeout releases the lock but does not stop the work (l2-node.ts:1594-1610). Fixture paths wait up to 600 seconds for the lease while they hold that lock (l2-sequencer-service.ts:2052; interactive-service.ts:1249). After a timeout, two engine operations can run at once.
- Engine proof workers can grow large before they restart. Each one recycles after 50 jobs (start-leviathan.ts:519). By the pool's own estimate of 60 MB per proof (proof-pool-types.ts:143-144), that is about 3 GB per worker across four workers. The memory sizing for the pilot host should count this.
- Messaging keys collide. Pharmacy keys are stored at index 10+i, which overwrites prescribers 10 to 15 (interactive-service.ts:908-920). eScripts at prescribing look up keys by those indices (2754-2755), so six prescribers' eScripts are encrypted with pharmacy keys.
- A reversal can change the engine's records without a ledger record. If the ledger step fails, the error is swallowed and the change stays: the fill is marked reversed and the accumulator rolled back (interactive-service.ts:3841, 3863-3867).
- Prescribe and dispense check the member's status in the engine's own copy (enrolled.lifecycle), not the ledger's lifecycle tree (interactive-service.ts:2477, 3056). The two can disagree after a restore or a failed termination.
- Committed pending claims never expire (l2-sequencer-service.ts:1437-1449). If a phone never proves an update, its claim stays in every checkpoint. The 14-day return-to-stock rule needs a way to cancel it.
- Registration sets the wallet ELIGIBLE on the ledger before the phone proves the credential mint (interactive-service.ts:1980, then the queue at 2043). If the mint never lands, the wallet stays ELIGIBLE with no credential.
- register-member is open to anyone (interactive-routes.ts:155). Its body has no size cap (interactive-routes.ts:2217-2219; request-body.ts:31), and it runs verify() on whatever proof it is sent. It needs a size cap and a rate limit before exposure.
- Two attestation keys live in one process. The node enables one from GOSSIP_SECRET (start-leviathan.ts:437). The engine has another from a literal seed and serves that one as the 'sequencer public key' (interactive-service.ts:647-649, 6066-6067). Which key a verifier should trust depends on the path. This is from reading the code only.

## What the engine should be in production

In production, the engine should be the plan's pricing and adjudication service and nothing more. It runs as its own program with its own listener, its own operator credential, its own encrypted and backed-up state, and one copy for the whole network (with a standby), outside every Leviathan node. It holds no member identity (true now for phone members) and no provider keys. It reaches the ledger only through signed sequencer calls. Lifecycle changes become signed insurer operations the sequencer checks and logs, and claims ride only on a proof the sequencer verifies. adminMutate, commitPendingClaim and direct tree reads leave the engine. At prescribing it prices the script from the sequencer's published NADAC list times quantity plus the plan's dispensing fee, using the approved plan's copay, limits and formulary, and counting the family's open scripts. It returns a quote and a fill proof that is kept. The sequencer verifies that proof against a pinned key and attaches the claim only when the member's wallet update reaches the proof's new root. The phone verifies the proof and reads the old and new totals before it signs. Prescribers and pharmacies prove their own steps with their own keys; the fill circuit is split so the engine proves the price and each provider signs its own step. Since hardware keys are deferred, use the stopgap: a key made on each provider's own machine, stored encrypted under a PIN. The routes bind the calling node to the provider named in the request. Suggested order: (1) now, fix the fixed-limits reset and bind the eligibility credential and copay to the approved plan; (2) keep and verify the fill proof, with the check on the phone; (3) price at prescribing with NADAC plus fee; (4) move provider keys out with the software stopgap, and split the fill proof; (5) move the engine into its own process before a second Leviathan node runs; (6) delete the fixture paths (seed provisioning, badges, literal attestation seed, PLAN-GOLD template, seed X25519 keys).

## Moving the engine into its own process

- What changes. Outside the sequencer the engine loses four in-process powers: direct reads of the wallet trees (interactive-service.ts:578-581), adminMutate with provision, setLifecycle and setWalletState (l2-sequencer-service.ts:1505-1531), commitPendingClaim (1439-1441), and the node's proving lock. It must call instead: the witness and wallet-state RPCs with a lease holder (l2-rpc-server.ts:1852-1876), new signed methods for set-eligible, terminate and commit-claim, the audit-event and batch calls as signed methods, and the sequencer's read RPCs, which already carry the D1 read gate. The 16 /node/* mirror routes can be dropped so clients read the sequencer directly.
- Benefit, security. About 10,000 lines of engine code and 65 routes stop running in the process that holds the trees. Consequence: a bug or break-in in an engine route can reach only the short method list an engine role is given, instead of a closure that can register wallets, change lifecycles and overwrite a wallet's credential root with no proof.
- Benefit, security, already partly delivered. B2 removed impersonation by preimage: the engine refuses to prove for a member with a device (interactive-service.ts:5465-5466) and every submitted proof is verified before any write (l2-sequencer-service.ts:302-321). Consequence: R3's stated reason is mostly answered. What remains is narrower: lifecycle writes, the unproven setWalletState, unverified claim amounts, and provider keys in engine memory. The move closes the first three paths for engine code; the B4 stopgap closes the fourth.
- Benefit limit, security. The person who runs the sequencer still has adminMutate in their own build, so the move does not stop a dishonest operator. Only phase E does: replicas that check before they apply (E7), a quorum under separate control (E4 and section 8 question 2), and the chain proof (E6). Consequence: describe the move to auditors as shrinking the trusted code; keep the claim that no one can write your state for after phase E.
- Benefit, audits and trust. Claim amounts reach the ledger only through the engine's in-process commit, and the RPC attaches them to the member's proof without checking them against any proof (l2-rpc-server.ts:893-906). Once the engine is outside, the only way in is an RPC call, and that call can require the engine's claim proof and verify it against a pinned key, the way A1 does for wallet updates. Consequence: every ledger change becomes a verified proof or a signed, logged admin act by a named role. This closes A-22 for the fill and is what the owner's decision (the claim proof is kept and verified) needs.
- Benefit, audits. adminMutate takes a closure and logs only a reason string (l2-sequencer-service.ts:1505-1551). A typed request, such as set wallet W to state S signed by the engine key, can be written to the WAL, sent to replicas and checked there. Consequence: the admin change log names a principal and can be replayed after a crash.
- Benefit, crash isolation. The engine owns the sequencer process's single o1js context; after it compiles, every other o1js call in that process stalls for good (PLAN:111-125; start-leviathan.ts:231-237). Consequence: today the sequencer can do no proof work in its own process, and a hang in engine proving shares a process with the ledger. Separated, the ledger process is free of that limit.
- Benefit, memory isolation. The WASM heap grows about 60 MB per proof and only worker recycling gives it back (proof-pool-types.ts:143-144). If the engine's pool is down, it proves inline in the sequencer and blocks the event loop (interactive-service.ts:1043-1046; start-leviathan.ts:548). Consequence: a pool failure becomes a memory leak and long stalls in the process that holds the ledger and both in-process replicas (start-leviathan.ts:594-642). In its own process the engine can be restarted on a memory threshold with no ledger restart.
- Benefit, memory sizing. Batch workers are sized from free memory with 400 MB reserved for the main process (start-leviathan.ts:297-318); the engine's 4 proof workers and its 10 compiled programs are added later and not counted (517-519, 553). Consequence: a production host can run out of RAM under load. Separate processes can each be sized and capped, or put on separate hosts.
- Benefit, load isolation. Pricing before the script is written means every prescriber composing a script asks the engine for a quote, and engine routes have no rate limit or body cap today (docs/audit/engine.md ENG-17). Consequence: separated, a burst of quotes or a slow proof slows quotes only. The ledger keeps taking proofs and serving pharmacies at pickup, which the owner now requires to be online.
- Benefit, scaling. Engine operations hold the node's one proving lock, which batches also take when no batch pool runs (interactive-routes.ts:415-1305; l2-node.ts:1302, 1594-1611). Consequence: today one engine operation at a time per sequencer, and a batch can wait behind a 30 to 180 s engine proof. Outside, the engine has its own lock and pool, and the sequencer's lock serves batches only.
- Benefit, scaling with partitions. Entity nodes already pick the right sequencer per wallet through PartitionRouter (entity-node-base.ts:86); the embedded engine sees only its local trees (interactive-service.ts:578-581). Consequence: with partitions on, an embedded engine cannot serve a member whose wallet sits in another partition. An external engine reuses the router and serves all of them. Running more than one engine still needs shared engine state; that is later work.
- Benefit, restart and recovery. Every engine deploy today restarts the ledger, which then runs the restore path A-25 flags (docs/audit/sequencer.md SEQ-02, SEQ-04), and waits out the engine's 3 to 5 minute compile in the same process (start-leviathan.ts:464-467). Consequence: pricing fixes, NADAC updates and plan rule changes would each restart the ledger. Separated, the engine restarts alone.
- Benefit, restart safety. After a restore whose trees did not match, the first routine engine call (register a member, terminate) runs adminMutate, which declares the rebuilt trees authoritative and publishes their roots (l2-sequencer-service.ts:1535-1539, 3237-3240). Consequence: a lossy restore can silently become the ledger's truth. Typed admin RPCs give a natural place to refuse admin writes until the trees are proven complete. The guard is small and could also be added in-process.
- Benefit, fit with the owner decisions. The phone already uses two paths: engine routes for its queued update and the sequencer RPC for witnesses and submission (member-routes.ts:106, 145, 165, 173). Consequence: the native app needs a second address and nothing else. The claim proof travelling with the queued update, checked on the phone before it signs, is the same work inside or outside, and the sequencer verifying that proof is the move's main new method.
- Benefit, fit with NADAC plus fee. The sequencer and the engine each load the full NADAC set into the same process (start-leviathan.ts:328-335; interactive-service.ts:144, 788-799), and the engine's price basis is NADAC times 1.2 (799), which does not match NADAC plus a dispensing fee. Consequence: a separate engine can own the price feed and reload it without touching the ledger; the sequencer keeps only the committed formulary root that proofs bind to.
- Benefit, fit with the engine giving up provider keys. The engine proves with pharmacy and prescriber preimages in memory (interactive-service.ts:2471, 3051, 3053, 3726, 5136) and signs attestations from a literal seed (647-649). Consequence: the B4 stopgap (providers prove their own identity on their devices and the engine checks that proof) plus the move leaves an engine process that holds plan data, prices and one service key, and nothing that can act as a member or provider. That is the section 3 target (PLAN:44).
- Cost, effort. The remaining coupling is about 20 tree reads, 5 adminMutate calls, 1 claim commit, 3 audit events, 3 in-process proof submissions, 1 mid-ceremony batch build, 17 route handlers that read the sequencer directly, 15 uses of the node's proving lock, the state file, the launcher, 10 node-server call sites and the device address. Consequence: about 2 to 3 sessions including a full secured run and a multi-member run. The identity work R3 counted as the long pole is already done by B2.
- Cost, throwaway work on fixtures. Three of those sites exist only for fixture members, for whom the engine still proves with stored preimages (interactive-service.ts:1249-1448, 5459-5545), and phase F deletes fixtures before tagging. Consequence: porting them to RPC is wasted effort if the acceptance harness can run on device members alone.
- Cost, latency. Each in-process call becomes a network round trip, perhaps 5 to 10 per fill. Proofs take 25 to 45 s (docs/AUDIT.md A-33) and verification about 4 to 6 s (PLAN:103-106). Consequence: tens of milliseconds added to an operation that takes tens of seconds. The quote at composing can come from the engine's own price and plan cache with no ledger call. It should still be measured once on the target host.
- Cost, new authentication. The engine needs its own role and key; the mechanism and the launcher pattern exist (node-roles.ts:17-63; start-leviathan.ts:735-755). Consequence: the engine key becomes a high-value secret, since it can commit claims and change lifecycles. Keep its method list short, require a verified proof for any claim commit, and keep the key out of child environments. Without hardware keys it stays an operator-held secret until a cloud key service is chosen.
- Cost, proving lease interplay. Today the engine queues for the lease in-process (interactive-service.ts:1249, 5496), its lifecycle writes wait inside the process (1448, 1980), and termination does not wait at all (4488-4489). Outside, lifecycle writes become methods that wait inside the sequencer, and a wait can run the full 120 s lease window, past the 30 s default request budget (l2-rpc-server.ts:508). Consequence: those methods must answer busy with a retry time, like the witness calls, and D8's one slot per principal must treat the engine as a principal. The termination gap closes by construction.
- Cost, consistency between two stores. The pending claim sits in the sequencer checkpoint and the matching pending wallet update in the engine's file, saved every 60 s (l2-sequencer-service.ts:2975-2976; start-leviathan.ts:508-514). Consequence: the split needs a claim commit keyed by the update ID that can be safely repeated, and a startup step where the engine rebuilds from the ledger. That also fixes a mismatch a hard crash can cause today, and 14-day prepared fills and mail-order windows need engine timers that survive restarts anyway.
- Cost, operations. Two processes to deploy, watch and back up, the engine's state file moves with it (start-leviathan.ts:476), and the sequencer's software identity is currently taken from the engine's compiled programs (556-561) and needs its own source. Consequence: modest, and it belongs in the pilot runbook.
- Timing, phase E is harder with the engine embedded. E1: the engine sees one partition. E3: adminMutate writes no WAL entry and takes a closure that cannot be logged (l2-sequencer-service.ts:1505-1551 versus 391-392), so engine lifecycle changes cannot be replayed after a crash. E4: in-process calls skip any client acknowledgment path. E5: the engine and its state file die with the leader, and the new leader has no engine. Consequence: each of these needs a special case for an embedded engine.
- Timing, the pilot needs the seam. The pilot safety net includes the WAL, and the WAL needs admin writes as typed records, which is the interface the move creates. Consequence: the seam work has to land before real members whether or not the process split does.
- Timing, B3 rewrites the same seam. Pricing at prescribing, pending settlements and reservations, pickup finalize, the 14-day return to stock and mail-order finalize at shipping all add new engine-to-ledger calls. Consequence: built in-process now and ported later, they are built twice. Built as signed RPC from the start, the split itself becomes mostly launcher work.
- Timing, live release. The native phone app and pharmacy systems will be built against fixed addresses. Moving the engine after go-live means a migration on a live system: a new address in shipped apps, a moved state file, new credentials. Consequence: it costs less before the pilot than after it.
- Timing, too early right now. The provider-key stopgap and B3 change the fill proof's inputs and the claim commit. Consequence: RPC methods written before them would be rewritten. Start right after them, or design B3's sequencer calls as RPC while doing B3.
- Timing, the case for waiting. The move does not block pickup, and a single operator can still change the sequencer until phase E, so the gain before phase E is real but partial. Consequence: if the pilot date cannot absorb 2 to 3 sessions, keep the seam before the pilot (no tree reads, adminMutate or commitPendingClaim from engine code, claim proof verified by the sequencer) and make the process split the first item of phase E. Waiting past the start of phase E costs more, because E1, E3, E4 and E5 each assume it.

**Timing recommendation.** Move the engine into its own process before the pilot with real members. Do it right after B3 and the provider-key stopgap, and no later than the start of phase E. While doing B3, build every new call from engine to ledger as a signed RPC under a new engine role: the claim commit, pending reservations, pickup finalize, the 14-day return to stock and mail-order finalize. The claim commit must carry the engine's claim proof, and the sequencer must verify it against a pinned key before it records the claim. Then remove the remaining tree reads, adminMutate calls and the proving-lock use from engine code. Spawn the engine as a child with its own key, listener and state file, and give the phone app and node servers its address. Expect 2 to 3 sessions. If the pilot date cannot take that, the seam above is the part that must land before real members, because the pilot's WAL needs typed admin writes and the owner's claim-proof decision needs sequencer verification. The process split can then be the first item of phase E. Do not go to production with engine code that can call adminMutate or commit unverified claim amounts. Separately and now: delete setWalletState if nothing legitimate needs it, and refuse admin writes while restored trees are not authoritative.

## Provider keys without buying hardware

The engine is the claims-processing program. In code it is the AdjudicationService class in src/adjudication/interactive-service.ts. Today it runs inside the Leviathan sequencer process and answers on the sequencer's port at /interactive/* and /node/* (src/nodes/start-leviathan.ts:469-470). It holds the plan's rules (formulary, benefits, accumulators), checks each script and fill against them, works out who pays what, makes the zero-knowledge proofs that show the math followed the rules, and keeps the working record of prescriptions and fills. Today it also holds the seed prescribers' and pharmacies' identity secrets and proves their identity for them; this work removes that.

- The core problem. A provider's wallet ID is a hash of its NPI and of its enrollment key hash. The NPI is public, so anyone who knows the enrollment key hash can prove to be that provider. Today the engine knows it for every seed prescriber and pharmacy, and the fill and prescription circuits require it as an input. With today's circuits, an engine that makes the claim proof has to hold provider secrets. So the circuits must change. The provider makes its own identity statement, and the engine checks it and keeps the evidence.
- Option A: the provider proves its own identity in zero knowledge. The provider node makes a small identity proof tied to the specific claim. The engine verifies it, or folds it into the fill proof by recursion. Good: all the evidence is one kind of proof. Costs: today's identity proof names only the wallet, so a new version must also commit to the claim, or one copied proof works forever. The provider's secret has to be in workstation memory every time it proves, which is the exposure B4 set out to remove. Passkeys and hardware keys cannot make this proof, because they sign on standard curves and cannot compute Poseidon. Recursion also adds work to a fill circuit that already takes 24 private inputs.
- Option B: the provider signs and the engine checks. The provider signs a digest of the script or the fill. The engine checks the signature against the key registered to that provider's wallet. Then it proves the claim with the provider's wallet ID as a public value, and keeps the signature with the proof. Good: the provider's private key can stay inside the device's secure hardware, so neither the engine nor the workstation's memory ever has it. It works with passkeys now and hardware keys later. Cost: the identity check sits beside the proof, so a checker verifies the proof and a short signature chain. The fill proof already outputs the claim data hash (entryCommitment), so the signature can be tied to exactly what was proven.
- Friction. A passkey prompt on every fill means a face, fingerprint or PIN check per fill, which is too much for a pharmacy doing hundreds a day. What works: one passkey unlock at shift start signs a short-lived session key, kept only in the node's memory, and the session key signs each claim. Ed25519 fits, since the code already signs requests with it and FIPS 186-5 approves it. The risk is that malware on the workstation during the shift can sign claims until the session ends. A hardware key used once per session has the same window, and that is the model B4's own friction budget chose for ordinary prescribing.
- Where the enrollment key lives. In this design it is needed only for rare steps: adding or removing a passkey, and rotating keys. So it can stay locked away. Lock it under each passkey's PRF secret (PRF is the web name for the hmac-secret feature B4 planned to use), and also under a printed recovery code. The locked copies can be stored anywhere, the insurer included, because nobody can open one without the provider's device or the code. PRF support as of 2026: Apple iCloud Keychain on macOS 15+ and iOS 18.4+; Google Password Manager in Chrome on Android; Windows Hello only on Windows 11 24H2 or 25H2 after the February 2026 update, and never on Windows 10. Daily signing needs no PRF. An older workstation can still sign with a passkey and rely on the phone or the recovery code to hold a locked copy.
- OS keystores on the provider node. DPAPI, the macOS Keychain and Linux Secret Service stop someone who steals the disk. They do not stop a program running as the same user, which can get the secret with no prompt. TPM-bound options (the Windows Platform Crypto Provider, or systemd-creds with tpm2 on Linux) keep a key on one machine, but they still hand it to local software with no person present. Node.js support is thin: keytar is unmaintained, and TPM access needs a native helper. Use the keystore to protect the node's own keys at rest, such as its transport key and its message decryption key, so the node can restart unattended. It cannot show that a provider approved a claim, so it must not serve as that proof.
- Phone app for providers. The provider's phone already works as a passkey for the workstation through the QR code flow, with no app to build. That needs Bluetooth on the workstation and internet on both devices. A provider app later can reuse the member app's key storage: the Secure Enclave on iPhone (P-256 keys, device only, biometric gate) and Android Keystore with StrongBox and a biometric prompt. That suits prescribers who work away from a desk. Release one does not need it.
- Compared with B4's hardware keys. Equal: the engine can no longer act as a provider. A stolen device is about as safe, since Windows Hello keys are held in the TPM with PIN lockout. Phishing protection is the same, since passkeys are tied to one web address. Weaker: a synced passkey (iCloud Keychain, Google Password Manager) also lives in the provider's cloud account, so that account's recovery process becomes part of what we trust. WebAuthn's backup flags show at registration whether a passkey is synced, so policy can require a device-bound one for daily signing. Weaker at shared counters: if staff share one Windows login, Windows Hello there is a shared factor, and each pharmacist then needs their own login or their own phone passkey. For non-controlled prescriptions this level is reasonable. For controlled substances it is not enough, and those are out of release one.
- Defects this change must fix whichever option is chosen. (1) Provider nodes send the engine a seed index and no proof, and use seed provider 0 when a wallet is unknown, so an unseeded pharmacy fills as a different pharmacy (pharmacy-routes.ts:666, prescriber-routes.ts:615-619). (2) The engine's fill route takes only a prescription ID behind a role key, so any pharmacy node can dispense any pharmacy's prescription (interactive-routes.ts:624-654). (3) A provider's signing key is registered first come with no proof of wallet ownership, and the operator can replace it (l2-rpc-server.ts:2008-2017). (4) At dispense the engine proves the status change with the prescriber's identity (interactive-service.ts:3159-3160). (5) Provider dashboards have no login (nautilus-app-server.ts:625-639). (6) The identity proof names only the wallet and can be reused (proof-gate.ts:49-51).
- Code changes for the recommended path. Circuits: remove the three provider identity inputs from the fill and reversal methods and from both prescription methods, and keep the wallet ID as a public value. Engine: delete the provider preimage maps, the badge creation with PIN 000000, the seed X25519 private keys and the three provider identity proofs. Check the signature chain instead and store it with the claim. Routes: require the signature of the prescription's own pharmacy or prescriber, using the wallet-signed route pattern from B2. Registry: a provider can register a key only with a zero-knowledge proof that the wallet's owner added it, and the operator override is removed. Provider node: a passkey login with PRF, a locked enrollment key, a memory-only session key, and a separate message decryption key, since today both the signing key and the decryption key derive from the enrollment key. Member phone: check the signature chain and the claim proof before it signs its wallet update. Remove the badge service, the resolve-indices route and the NPI-derived seed keys from every runtime path.
- Upgrading to hardware keys without re-enrolling. The wallet ID depends on the enrollment key, and the enrollment key stays the same. A hardware key is added later as one more passkey through the same add-a-key step: unlock the enrollment key with an existing passkey, prove the new key's binding, and lock one more copy under the hardware key's hmac-secret. Then retire the platform passkeys if policy calls for it. The wallet ID, insurer credentialing and claim history stay as they are. For controlled substances later, only policy changes: require a certified hardware key and a touch at each controlled signing. One limit: if a workstation was compromised while the enrollment key was unlocked, adding hardware does not undo that. Reviving WalletMigrationProgram for providers covers that case, and the plan already revives it for members in C3.

**Recommendation.** Use the passkeys providers already have. Nothing needs to be bought. At credentialing, the provider's node makes a fresh random enrollment key. The provider registers two passkeys with PRF: Windows Hello on the workstation, and their phone (Google Password Manager or iCloud Keychain) over the QR flow. The enrollment key is then locked under each passkey and under a printed recovery code, and kept cold. The provider proves once, in zero knowledge, that its wallet's owner added these passkeys. The insurer's credentialing stays as the human check. Day to day, a pharmacist or prescriber unlocks once at shift start with face, fingerprint or PIN. That unlock signs a session key that lasts at most 12 hours and lives only in memory. The session key signs each script and each fill. The engine checks this signature chain, then makes the claim proof with the provider's wallet ID as a public value. The engine never holds a provider secret. The signatures are stored with the proof. The member's phone checks the chain and the proof before it signs its wallet update. Use OS keystores only to protect the node's own keys at rest. Leave the provider phone app to the native-app program. The engine-side work is listed in the analysis: change the circuits, delete the engine's provider keys, require the right provider's signature on engine routes, require an ownership proof when a provider registers a key, add a passkey login to provider dashboards, and remove the seed-index fallbacks. Hardware upgrade: each hardware key is added later as one more passkey with its own locked copy of the enrollment key. Wallet IDs, credentialing and history stay the same, so nobody re-enrolls. My estimate is 3 to 5 sessions. Before building, test PRF on the pilot's actual workstations and phones, because the support figures come from third-party tests.

- Google Password Manager passkeys support PRF in Chrome, Edge and Samsung Internet on Android, including cross-device use. Firefox for Android added PRF in 149 (March 2026). Google Password Manager is the default passkey provider on Android. (https://www.corbado.com/blog/passkeys-prf-webauthn; https://groups.google.com/a/chromium.org/g/blink-dev/c/iTNOgLwD2bI; https://developers.google.com/identity/passkeys/supported-environments)
- Gaps: the Chrome profile authenticator has no PRF, several third-party password managers return no PRF value, and a browser saying it supports PRF does not guarantee a value comes back. (https://www.corbado.com/blog/passkeys-prf-webauthn)
- The cross-device (hybrid) flow lets a phone act as the passkey for a computer through a QR code, with Bluetooth as a proximity check. Both devices need internet, and the computer needs Bluetooth. (https://thalesdocs.com/oip/fido2-sdk/fido2-sdk-hybrid-transport/; https://www.corbado.com/blog/webauthn-passkey-qr-code)
- Windows Hello keys are held in the TPM, and the TPM's anti-hammering locks the device after too many wrong PIN guesses. (https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/faq)
- WebAuthn's Backup Eligible and Backup State flags tell the server at registration whether a passkey is synced across devices or bound to one device. (https://w3c.github.io/webauthn/ (Terminology); https://mojoauth.com/blog/webauthn-be-bs-flags-synced-vs-device-bound-passkey)
- DPAPI protects data at rest against disk theft and other users. Any process running as the same user can decrypt it without a prompt. (https://docs.racket-lang.org/dpapi/security-best-practices.html; https://textslashplain.com/2020/09/28/local-data-encryption-in-chromium/)
- node-keytar, the common Node.js binding to Windows Credential Manager, the macOS Keychain and libsecret, is unmaintained. Zowe ships a Rust drop-in replacement. (https://cdn.jsdelivr.net/npm/@zowe/secrets-for-zowe-sdk@8.33.4/src/keyring/EXTENDERS.md)
- On Linux, systemd-creds --with-key=tpm2 encrypts a service secret so that only that machine's TPM can decrypt it. (https://man7.org/linux/man-pages/man1/systemd-creds.1.html)
- On Windows, the CNG Platform Crypto Provider creates non-exportable keys inside the TPM. Node.js has no built-in binding for it. (https://learn.microsoft.com/en-us/windows/win32/api/Ncrypt/nf-ncrypt-ncryptcreatepersistedkey; https://docs.digicert.com/zf/device-trust-manager/tutorials/generate-and-manage-tpm-protected-keys-in-windows-using-powershell.html)
- iPhone Secure Enclave keys are P-256, stay on the device that made them, and can be gated by an access-control policy such as biometrics. (https://developer.apple.com/tutorials/data/documentation/security/protecting-keys-with-the-secure-enclave.md)
- Android Keystore keys can be StrongBox-backed and require user authentication. OWASP recommends binding them to BiometricPrompt through a CryptoObject. (https://developer.android.com/reference/android/security/keystore/KeyProtection.Builder; https://mas.owasp.org/MASTG/best-practices/MASTG-BEST-0036/)
- FIPS 186-5, in force since February 3, 2023, approves EdDSA, including Ed25519. (https://www.govinfo.gov/content/pkg/FR-2023-02-03/html/2023-02273.htm; https://csrc.nist.gov/Projects/digital-signatures)

- Does setWalletState have any legitimate caller? None exists in src today.
- Will the pilot run the engine on the same host as the sequencer or on its own host? This decides the memory sizing for both proving pools.

The other route is a Pallas session key, which is cheap in a circuit but not FIPS-approved. Measure first.
