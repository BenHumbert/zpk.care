# Proof-and-crypto integrity audit — zpk.care

Session 2 of the review program. Scope: where ZK proofs are and are **not** cryptographically verified, and whether unverified submissions, settlement rewrites, or the committed audit chain let a dishonest input change committed state or financial outcome. PHI and route-auth are covered by other agents (cited only where they compound). No source file was modified. Every `file:line` was read in the working tree; live claims were checked against the running sequencer (`:3030`, `l2Only`, plain `L2Node`, uptime ~29 h, 20 proofs / 19 batches / 35 wallets at probe time).

Abbrev: `seq`=`src/l2/l2-sequencer-service.ts`, `node`=`src/l2/l2-node.ts`, `bp`=`src/l2/batch-program.ts`, `cp`=`src/l2/chain-program.ts`, `audit`=`src/audit/audit-service.ts`, `claim`=`src/l2/claim-accumulator-service.ts`, `S`=`src/adjudication/interactive-service.ts`, `PW`=`src/adjudication/proof-pool-worker.ts`, `nfc`=`src/credentials/nfc-attestation.ts`, `start`=`src/nodes/start-leviathan.ts`, `rpc`=`src/l2/l2-rpc-server.ts`.

## Live submitProof no-op probe (headline question)

Goal: does the sequencer accept a structurally-valid but cryptographically-bogus `StateTransitionProof` because `proof.verify()` is a no-op outside a circuit? Executed only rejections; captured status before/after to prove zero mutation.

Exact calls (to `POST http://localhost:3030/rpc`) and responses:
- `l2_getStatus` **before**: `walletCount=35, proofsAccepted=20, pending=0, batches=19, regRoot=100765564684337544913690…`
- A1 `params:{}` → `-32602 "Missing or invalid proofJson parameter"` (shape gate, `rpc:757`).
- A2 `proofJson:"not-an-object"` → same `-32602` (`rpc:757`).
- A3 `proofJson:{}` → `-32603 Internal error` (throws inside `StateTransitionProof.fromJSON`, `rpc:760`).
- B `proofJson:{maxProofsVerified:0, proof:"ZmFrZXByb29m", publicInput:[], publicOutput:["11111","22222","33333","44444","55555"]}` → `-32603 Internal error` (fails at `Pickles.proofOfBase64`, `proof.js:106`).
- `l2_getStatus` **after**: identical (`walletCount=35, proofsAccepted=20, pending=0, batches=19`, same root) → **no state change**.

Result, stated precisely:
- A hand-built "proof" never reaches `proof.verify()` or the root check: `fromJSON` first runs `Pickles.proofOfBase64`, a **structural decode** (not a cryptographic validity check), which rejects any non-Pickles blob. So the empirical rejection layer for forged input is the decode, and — per o1js's own source (`proof.js:89`: *"Executing it outside of a circuit will have no effect"*) — `proof.verify()` at `seq:293` is provably a no-op.
- **Not executed (to avoid mutating/poisoning real state):** submitting a *decodable* real proof whose `publicOutput.oldRoots` were altered to equal the current roots. Reasoned outcome from `seq:293→324→374-378`: it would pass `verify()` (no-op) and the root equality check, then be **applied** (receipt + audit-chain advance + sequence increment + gossip), and only fail in-circuit at batch time (`bp:91`) with no `l2Only` rollback — i.e. acceptance is gated by **root equality, not cryptography**. No decodable spare `StateTransitionProof` exists on disk (InMemoryStore; checkpoints hold only `BatchProof`), so this could not be shown without a real mutation; the file:line above proves the mechanism.

## What the batch/chain proof actually guarantees

A `ChainProof` lets an outside verifier trust exactly this: there exists a sequence of `BatchProof`s (each verifying its `StateTransitionProof`s in-circuit, `bp:91-92,131-132`) that chains `oldRoot→newRoot` consistently (`cp:143-157`), and each `StateTransitionProof` proves that *someone knew a 6-field preimage hashing to the walletId* being inserted/updated and that the registry+lifecycle Merkle update for that slot is arithmetically correct (`state-transition.ts:83-105,175-217`). In short: **the wallet-registry/lifecycle tree evolved by a series of preimage-authenticated slot writes** — an authenticated set with correct Merkle bookkeeping. It does **not** prove: that any walletId belongs to a real, enrolled, non-revoked person (any preimage satisfies the circuit; no enrollment/token binding); eligibility, formulary tier, prior-auth, step-therapy, or in-network status (those proofs are discarded, ZK-2); **any financial amount** — `patientPay`/`planPay` appear in no circuit the ChainProof covers (only in the discarded AccumulatorFulfillment proof, and rewritten after even that, ZK-3); that the claim ledger, accumulators, or audit-chain amounts are correct or complete (ZK-4/5/6); or that the stored `batchProofJson` even corresponds to the sequencer's served state (`finalizeBatch` never cross-checks, ZK-1). The six admin fields and `auditChainHash` are free private inputs each block and are not linked across blocks (`cp:42-45`), so the ChainProof also does not anchor the audit chain.

## Open questions

- Is `treesAuthoritative` currently true or false on the restored live node? It decides whether ZK-1 lets an attacker set an *arbitrary* registry root (`seq:1452,1469,1485` skip the recompute asserts when false, `seq:3059`) or only inject arbitrary walletIds. No RPC exposes it; determining it safely needs a read-only hook, not a probe.
- Who is the intended verifier of the discarded claim-flow proofs (ZK-2)? Nothing in the running topology consumes them; is a relying-party verifier planned, or is the proof delegate (`:4040`, unused) meant to carry them?
- Is the family-pool split (ZK-3) meant to be re-proved? Current code commits the pre-pool split in the forest and the post-pool split in the ledger.
- Should `l2_submitProof` be OPEN at all? It is the one state-mutating RPC reachable unauthenticated through every node proxy and the explorer.
- Is `enrichAuditEvent` (ZK-6) dead by intent, or was a call site dropped? Its absence makes two of the three audit "verifications" vacuous.
