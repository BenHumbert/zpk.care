## 4. Auth model (what a check actually is)

- **Sequencer RPC** (`rpc:689-716`): Bearer `ZKTRIDENT_ADMIN_TOKEN` whenever `unsecureMode` or the admin-key registry is empty; default-deny when no token. Ed25519 `X-Admin-Signature: nodeId:ts:sig` over `method|sha256(params)|ts` (±30 s, no nonce) applies only once a key is registered, and nothing in the tree registers a genesis key or calls the admission RPCs, so the deployed sequencer runs Bearer mode. Non-RPC admin routes and the engine's 9 ADMIN routes use `checkAdminAuth`, whose Ed25519 message is the constant `admin-endpoint|{}|ts` (`rpc:2661-2671`).
- **Nautilus `adminOnly`** (`AS:198-205`): Bearer compared timing-safe against the node's token. The Ed25519 client path (`AS:187-192`) signs `method:path|ts|X-Content-Hash` where the hash comes from the caller's header and is never recomputed; `registerClientKey` (`AS:212`) has no callers, so this path is dead.
- **Employer node / HR Tool:** employer node Bearer token from the orchestrator; HR Tool uses a passphrase session (`requireWorkspace`/`requireGroup`) and presents the admin token it holds encrypted in its workspace (A7); its dashboard sends no header. `ZKTRIDENT_UNSECURE` is read only by `start-leviathan.ts:80`; the employer and provider launchers ignore it (Bearer mode regardless).
- **Bind and CORS** (since A2, 2026-10-17, `src/security/network-policy.ts`): one policy module for every listener. Bind defaults to `127.0.0.1`; `ZKTRIDENT_HOST` overrides and a wider bind warns at boot. CORS defaults to the local dashboard origins **with ports** (`localhost` and `127.0.0.1` × 3030/3031/3032/4001-4004/4040/8000); an origin not on the list and a request with no `Origin` get **no** `Access-Control-Allow-Origin` header, where the old code sent the literal `null` and so granted every null-origin context. `ZKTRIDENT_CORS_ORIGINS` overrides; `*` is honoured only where the caller permits it, which is the sequencer in `ZKTRIDENT_UNSECURE` and nowhere else. No route handler sets the header itself any more (81 wildcard overrides removed, 77 of them in `interactive-routes.ts`). TLS: set `ZKTRIDENT_TLS_CERT` + `ZKTRIDENT_TLS_KEY` and the listener serves HTTPS; unset it serves HTTP, which is why the default bind is loopback.
- **Enrollment codes and signed node-to-node requests** (since A6, 2026-10-17, `src/onboarding/enrollment-code.ts`, `src/security/signed-request.ts`, `src/security/rate-limit.ts`): a code is `PPPP-XXXX-XXXX-XXXX-XXXX`, 80 random bits in Crockford base32 behind a 4-character routing prefix derived from the issuing employer's ID, with one canonical spelling that the member node computes where the code is typed. The insurer resolves a code to its employer by prefix from the sequencer's tenant registry and never fans out; its probe to `/tokens/:id/validate` is signed with the A9 key in the existing `X-Admin-Signature` / `X-Content-Hash` format, and the employer verifies it against the insurer key in its own attestation, over the body actually received, inside a 30 s window with a replay cache. The oracle consumes the code the moment the PIN verifies and learns no wallet ID. `signed-request.ts` recomputes the content hash from the body, which the admin path does not (AUTH-14); moving admin auth onto it is A9's remainder. `rate-limit.ts` is a keyed sliding window.
- **HR Tool on the employer's machine, and tenants that die with their parent** (since A7, 2026-10-17): the orchestrator spawns only the employer node, directly from the node binary with tsx's loader (one process, no npx, no shell) and with `ZKTRIDENT_PARENT_PID`, which `src/nodes/parent-watchdog.ts` polls so a tenant exits when the insurer process is gone; `ZKTRIDENT_UNSECURE` is stripped from what it inherits. Activation returns `hrToolSetup` steps instead of a hosted URL, and the sequencer's tenant registry no longer requires `hrToolUrl`. The HR Tool (`src/tools/hr-tool-server.ts`) is set up once with `POST /api/setup` (employer node URL, admin token, ≥ 12-character confirmed passphrase), stores the token encrypted beside its client key, unlocks through `src/security/attempt-limiter.ts` (three free, doubling to fifteen minutes, plaintext counter, never a wipe), returns PINs once at import, never lists or exports them, offers a re-authenticated audited `POST /api/employees/:hash/pin`, and writes hashes and counts to its audit log rather than employee IDs or search terms. `GET /groups*` on the employer node is admin.
- **The fixture directory is a static file, and the console is the operator** (since B1 first half, 2026-10-17): `src/data/fixture-directory.ts` is the projection the engine used to embed in `GET /interactive/state`; the explorer serves it at `/fixtures.json` beside the console's pages, built on first request. The dump keeps the formulary's live state and the plan block and carries no person records other than enrolled members. `visualizer/src/js/interactive/state-client.js` is the console's one way to load state (dump + fixtures, merged into `demoData`), and `operator-auth.js` attaches the operator token to every `/interactive/` request, prompting once on a 401. The second half of B1 began the same day; step one is the next bullet.
- **The engine lives in `src/adjudication/`** (since B1 step one, 2026-10-17): `interactive-service.ts`, `interactive-routes.ts` and the proof pool moved out of `visualizer/engine/` with their names (the names, the `/interactive/*` paths and `registerInteractiveRoutes` are renamed together in the naming pass after the program). `start-leviathan.ts` imports them statically; the path-string import inside a try/catch marked optional is gone, so an engine that cannot load is a boot failure. The engine is under `tsc` with the rest of `src/` (its 28 errors fixed; one was a real bug, the group enrolled-count that never incremented). The routes take an `NfcReader` from `nfc-port.ts`; the USB bridge stays in `visualizer/engine/` (its `node-hid` dependency is the visualizer's) and implements it, so nothing under `src/` imports from `visualizer/`; `tests/engine-location.test.ts` asserts that. Step two (own listener, authorised sequencer calls, identity out) rides phase B.
- **One credential per principal** (since A9 remainder, 2026-10-17, `src/security/node-roles.ts`, `src/security/request-body.ts`, `src/nodes/sequencer-fetch.ts`): the operator's `ZKTRIDENT_ADMIN_TOKEN` is accepted by the sequencer only. The launcher keys every child it spawns (Ed25519, generated per process, never on disk; `ZKTRIDENT_NODE_ID` + `ZKTRIDENT_NODE_KEY_SEED`), registers the public half on its RPC server with a role before the spawn (`registerNodeKey`, ephemeral, never checkpointed), and hands children an environment with none of its secrets (`childEnvironment`; explorer, prover and proof workers included). `L2RpcServer.authorize` takes the operator's bearer or a registered key's signature as alternatives and authorises a signature by role (`RPC_METHODS_BY_ROLE`, `ROUTES_BY_ROLE`; wrong role 403 `RPC_FORBIDDEN`). Every signature is `signed-request.ts`'s and covers method, path and body; the body is read once per request and cached. Nodes sign outbound calls with `sequencerAuthHeaders`/`signedFetch`/`sequencerClientOptions`; the insurer node's own routes take `ZKTRIDENT_INSURER_ADMIN_TOKEN` (HMAC-derived from the operator's when unset); member, prescriber and pharmacy nodes hold no token. Node servers verify with the same verifier (AUTH-14 closed); the employer node registers the HR Tool's client key (`/admin/client-keys`) and the HR Tool signs from setup on. Children are spawned without a shell and watch their parent.
- **Salted identities, redeem before derive, two recovery cards** (since Step 2 commit one, 2026-10-18): `hash-utils.ts` `hashIdentityField`/`hashIdentityDate` salt every member identity field hash with a per-device salt (`generateIdentitySalt`, kept in `nautilus-state.enc`, never in a response); the circuits are unchanged because they take the field hashes. `/onboarding/redeem` asks the insurer's `/enrollment/process` with the code and PIN hash and no wallet; the insurer redeems with the employer (A6) and answers the real group and plan hashes, which the wallet is derived with; `/onboarding/enroll` calls `/enrollment/complete`, which binds the wallet and files the recovery deposits. `recovery-card.ts` v3: `splitEnrollmentKey`, `issueRecoveryCards`, `recoveryPinVerifier`; the insurer's `/recovery/release|revoke|deposit` with `attempt-limiter.ts`; `/onboarding/recover` and `/recovery-card/issue` on the member node. Fixtures use `fixtureIdentitySalt(seed)`.
- **The engine's door and the real plan** (since Step 2 commit two, 2026-10-18): `/enrollment/complete` resolves the plan from the code's hash against `l2_getPlans` and posts `POST /interactive/approve-member` (admin-gated; insurer role in `node-roles.ts`) signed with the insurer's node key; the engine keeps `approvedMembers` in memory and in its checkpoint. `registerMemberFromEnrollment` throws `RegistrationRefused` (403 no approval; 409 not REGISTERED on the ledger, read from the sequencer's lifecycle tree) before anything is provisioned, and binds `planId`, `groupId` (the group hash), accumulator limits and the network from the approval through `bindPlan(plan, providers)`; `PLAN_NETWORKS`/default plan apply only to the console's fixture enrollment. The state dump's member entry carries `accumulator.limits`. Since B8 (A-34) the approval also carries the employer's opaque family hash, and the engine binds the member's family from it.
- **The wallet speaks for itself** (since A10b, 2026-10-18): `src/security/wallet-key.ts` derives each wallet's Ed25519 signing key from the enrollment key (HKDF, its own label; a sibling of the X25519 encryption key), registered as `signingPublicKeyHex` on `l2_registerEntity` and owned by the wallet (set once; the operator changes it; `l2_credentialProvider` and a proof's display metadata keep it). `L2RpcServer.WALLET_SIGNED_METHODS` names the wallet each of `l2_storeMessage`, `l2_registerPcpAssignment`, `l2_requestAttestation` speaks for; `authorizeWallet` accepts only that wallet's signature. `L2SequencerService.lifecycleStateOf` decodes a wallet's lifecycle leaf; `requestAttestation` states it and refuses a revoked wallet. `L2Client` takes a per-call signer; `EntityNodeBase.walletSigner` (wired by `NautilusAppServer.setEntityNode`) signs every node's `storeMessage`/`requestAttestation`; the member node serves `POST /attestation/request`; `src/nodes/provider-registration.ts` registers a provider node's entity with both keys at boot (A-30) and the badge tap uses it; a node registers only entities of its own kind and never credentials one (A-32). Rule refusals travel as `RequestRefused` (`src/l2/request-refused.ts`) with their message.

**5.1 Employer onboarding.** Insurer `POST /plans` (ADMIN) → `l2_storePlan`/`l2_publishPlanOverlay`.
