## 4. Auth model (what a check actually is)

- **Sequencer RPC** (`rpc:689-716`): Bearer `ZKTRIDENT_ADMIN_TOKEN` whenever `unsecureMode` or the admin-key registry is empty; default-deny when no token. Ed25519 `X-Admin-Signature: nodeId:ts:sig` over `method|sha256(params)|ts` (±30 s, no nonce) applies only once a key is registered, and nothing in the tree registers a genesis key or calls the admission RPCs, so the deployed sequencer runs Bearer mode. Non-RPC admin routes and the engine's 9 ADMIN routes use `checkAdminAuth`, whose Ed25519 message is the constant `admin-endpoint|{}|ts` (`rpc:2661-2671`).
- **Nautilus `adminOnly`** (`AS:198-205`): Bearer compared timing-safe against the node's token. The Ed25519 client path (`AS:187-192`) signs `method:path|ts|X-Content-Hash` where the hash comes from the caller's header and is never recomputed; `registerClientKey` (`AS:212`) has no callers, so this path is dead.
- **Employer node / HR Tool:** employer node Bearer token from the orchestrator; HR Tool uses a passphrase session (`requireWorkspace`/`requireGroup`), dashboard sends no header. `ZKTRIDENT_UNSECURE` is read only by `start-leviathan.ts:80`; the employer and provider launchers ignore it (Bearer mode regardless).
- **Bind and CORS** (since A2, 2026-10-17, `src/security/network-policy.ts`): one policy module for every listener. Bind defaults to `127.0.0.1`; `ZKTRIDENT_HOST` overrides and a wider bind warns at boot. CORS defaults to the local dashboard origins **with ports** (`localhost` and `127.0.0.1` × 3030/3031/3032/4001-4004/4040/8000); an origin not on the list and a request with no `Origin` get **no** `Access-Control-Allow-Origin` header, where the old code sent the literal `null` and so granted every null-origin context. `ZKTRIDENT_CORS_ORIGINS` overrides; `*` is honoured only where the caller permits it, which is the sequencer in `ZKTRIDENT_UNSECURE` and nowhere else. No route handler sets the header itself any more (81 wildcard overrides removed, 77 of them in `interactive-routes.ts`). TLS: set `ZKTRIDENT_TLS_CERT` + `ZKTRIDENT_TLS_KEY` and the listener serves HTTPS; unset it serves HTTP, which is why the default bind is loopback.
- **Enrollment codes and signed node-to-node requests** (since A6, 2026-10-17, `src/onboarding/enrollment-code.ts`, `src/security/signed-request.ts`, `src/security/rate-limit.ts`): a code is `PPPP-XXXX-XXXX-XXXX-XXXX`, 80 random bits in Crockford base32 behind a 4-character routing prefix derived from the issuing employer's ID, with one canonical spelling that the member node computes where the code is typed. The insurer resolves a code to its employer by prefix from the sequencer's tenant registry and never fans out; its probe to `/tokens/:id/validate` is signed with the A9 key in the existing `X-Admin-Signature` / `X-Content-Hash` format, and the employer verifies it against the insurer key in its own attestation, over the body actually received, inside a 30 s window with a replay cache. The oracle consumes the code the moment the PIN verifies and learns no wallet ID. `signed-request.ts` recomputes the content hash from the body, which the admin path does not (AUTH-14); moving admin auth onto it is A9's remainder. `rate-limit.ts` is a keyed sliding window.
- **`/rpc` proxies** (entity nodes and the explorer): on, forwarding only the methods that role's own dashboard calls (`PROXY_METHODS_BY_ROLE`) — member 35, explorer 45, pharmacy/prescriber/insurer 15, employer 3. A method off the list gets 403; `ZKTRIDENT_RPC_PROXY=0` closes the proxy entirely and it then answers 404; a role with no list gets no proxy. They are needed: `dashboard-member/rpc.js` sets `baseUrl = location.origin`, so its 29 sequencer calls go through the node unless a sequencer URL is stored, and the explorer page has no other path. `dashboard-leviathan` is served by the sequencer itself, so its 23 calls are same-origin to the real API, not proxied.
- **Signatures that are real:** employer + insurer Ed25519 on attestations (`l2_registerEmployer`, `rpc:1344-1345`; insurer key read from the attestation itself, `employer-attestation.ts:146-147`), NFC attestations (verified against the key embedded in the attestation, `nfc-attestation.ts:258-270`), quorum votes (dormant).

## 5. The pill pipeline, process by process

**5.1 Employer onboarding.** Insurer `POST /plans` (ADMIN) → `l2_storePlan`/`l2_publishPlanOverlay`. Browser generates an extractable Ed25519 key (`dashboard-marketplace/app.js:402`, memory only, regenerated on refresh) → `POST /marketplace/api/apply` (10/min global) → `upload-document/:id` (PDF ≤ 5 MB) → insurer `approve` (ADMIN) → `GET agreement/:id` → `POST sign/:id` (employer signature checked `MK:582`; insurer counter-signs with `insurerSign(message, adminToken)` `MK:588-595`) → `l2_registerEmployer` (ADMIN; v2 shape, monotonic `attestationSeq`) → `POST activate/:id` → `orch` spawns employer node + HR Tool, `l2_registerEmployerNode` (fingerprint only) → `GET activate-status/:job` returns the employer admin token (`MK:828`) → employer `POST /groups` (ADMIN; attestation fail-closed, plan authorized) → HR Tool `/api/unlock` → `/api/group/select` (creates the 32-byte group seed, `hr-tool-server.ts:499-503`) → `/api/import` CSV: per row `POST employer /tokens/generate {groupId, employeeIdHash, familyIdHash, validUntil}` then `/tokens/:id/set-pin-hash` (`:676-681, 707-709`) → `GET /api/export/tokens` returns code + plaintext PIN (`:846-848`). Token IDs are `TOKEN-${Date.now()}-${counter}` (`token-authority.ts:130`).

**5.3 PCP.** `:4001 /pcp/assign` (device only) → `/proof/pcp-assignment`: `l2_getWalletState`, `l2_getWalletWitnesses`, prove wallet update on device, `l2_submitProof`, `l2_syncWalletState` (verify-only), `l2_registerPcpAssignment` (OPEN, no proof, RPC-server memory `rpc:239`). **5.5 Fill and settle.** `:4003 /prescriptions/list` (pharmacy index defaults 0, `pharmacy-routes.ts:453`) → `/dispensing/mark-filled` → `/interactive/mark-filled` (any caller) → `/dispensing/dispense` (quantity defaults 30, `:524`) → `/interactive/fill` (202, job cache) → `dispensePrescription` (`S:2611-3186`): status FILLED/partial, quantity bounds, costs default AWP×qty+200 and caller values unvalidated (`S:2665-2667`); proofs ProofGate pharmacy, Prescription status, AccumulatorFulfillment (`S:2685-2811`; only its publicOutput is read `S:2822-2824`, proof discarded); family pooling rewrites pay after the proof (`S:2901-2920`) so claim metadata (`S:3008-3009`) and the settlement commitment (`S:2972-2977`) disagree → member wallet update proved by the engine from the stored 6 inputs with 4 retries (`S:5058-5127`) → `submitProof` with `ClaimSubmissionMetadata` → claim leaf (duplicate member+ndc+pharmacy+date returns the old leaf, `claim-accumulator-service.ts:110`, receipt points at it `seq:456`) → `forceBatch` → `:4003 /dispensing/fill-status`.

**5.6 Batch.** Timer/eager cycle (`node:1177-1240`) → `prepareBatch` (`seq:698-781`, ≤ 2 chainable transitions) → pool worker `wrapSingle`/`wrapPair`/`mergeBatches` (+ `ChainProgram.genesis/advance`) → `finalizeBatch` (`seq:790-896`) stores `batchProofJson` verbatim, marks receipts settled, checkpoints.
