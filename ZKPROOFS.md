## 1. What this document is

zpk.care is not a description of a zero-knowledge claim system. It is a working one. This document explains, with citations to the actual source files, what every proof does, how the proofs compose, what state they commit to, and what engineering choices were necessary to make a recursive proof system run on real hardware against the constraints of the underlying proof framework.

The reader is assumed to be technical but not necessarily a cryptographer. Where prerequisite knowledge is needed (Poseidon, Merkle witnesses, recursive SNARKs) the relevant context is given inline.

## 2. Cryptographic foundations

Everything in this system is built on three primitives.

**The Pasta field.** All values inside a proof are elements of the Pallas base field used by Mina's Kimchi proof system (equivalently, the scalar field of Vesta, the inner curve in the Pasta cycle). The TypeScript representation is the `Field` type in [o1js](https://github.com/o1-labs/o1js). Field elements are roughly 255-bit unsigned integers modulo a prime. They are the only data type that exists inside a ZK circuit.

**Poseidon.** A SNARK-friendly hash function. Cheap inside a circuit (a few hundred constraints) and collision-resistant outside. Used everywhere: wallet derivation, Merkle leaf commitments, state-tree roots, audit chain hashes, and the GlobalState commitment.

**Pickles / Kimchi.** Mina's recursive proof system. A `ZkProgram` compiles to a Kimchi circuit. Each `ZkProgram` method can verify up to two other Kimchi proofs as part of its own constraint system (the `maxProofsVerified = 2` setting). Proofs are ~22 KB and verify in milliseconds.

On top of these primitives sit Merkle trees (also from o1js, with circuit-compatible `MerkleWitness` types) and circuit-compatible state machines using `Provable.if` and `Provable.switch`.

## 3. The wallet model

A wallet in zpk.care has no private key. Its address (the `walletId`) is itself a Poseidon hash of identity data plus a device-only secret called the **enrollment key**. Access is demonstrated by a ZK proof of knowledge of the preimage.

Defined in [src/wallets/wallet-derivation.ts](src/wallets/wallet-derivation.ts):

```ts
walletId = Poseidon.hash([domainTag, ...hashedIdentityFields, hash(enrollmentKey)])
```

There are four domain tags so identical identity data cannot collide across roles:

| Tag | Entity | Preimage fields |
|-----|--------|-----------------|
| `Field(0)` | Member | `[cardholderIdHash, dobHash, firstNameHash, lastNameHash, enrollmentKeyHash, groupIdHash]` (6) |
| `Field(1)` | Prescriber | `[qualifierCode, prescriberIdHash, enrollmentKeyHash]` (3) |
| `Field(2)` | Pharmacy | `[qualifierCode, serviceProviderIdHash, enrollmentKeyHash]` (3) |
| `Field(3)` | Representative (AOR) | `[qualifierCode, representativeIdHash, enrollmentKeyHash]` (3) |

The **enrollment key** is a 256-bit random secret generated by `generateEnrollmentKey()` on the participant's own device. It is never transmitted, never logged, and never stored on the network. The insurer enrolls a wallet without ever learning the key.

This produces a very specific threat property: **a full breach of all identity data does not compromise wallets**. The attacker reconstructs every Poseidon input except `hash(enrollmentKey)`, and there is no shortcut around the hash. The wallet remains controlled by whoever holds the key.

The date of birth is hashed through Poseidon (`hashDate`) before entering the wallet derivation specifically to prevent brute-forcing the ~36,500 possible DOB values from a known `walletId`. See the H4 fix comment in [src/wallets/wallet-derivation.ts:115](src/wallets/wallet-derivation.ts#L115).

Members are bound to an employer group through `groupIdHash`. Changing employers means a new ceremony and a new wallet by design. This prevents one employer's plan from being silently used to fill prescriptions under another's roster.

## 4. The ZkProgram catalogue at a glance

Every proof in the system is produced by exactly one of the following `ZkProgram`s. Each row is a real file you can open and read.

| Program | File | Recursive? | Public output | Role |
|---|---|---|---|---|
| `ProofGateProgram` | [src/wallets/proof-gate.ts](src/wallets/proof-gate.ts) | No | `walletId` | Prove ownership of a wallet (4 methods, one per entity type) |
| `StateTransitionProgram` | [src/engine/state-transition.ts](src/engine/state-transition.ts) | No | `TransitionOutput` | Register a wallet or update its state (wallet ownership inlined) |
| `CredentialProgram` | [src/credentials/credential-program.ts](src/credentials/credential-program.ts) | Yes (verifies `ProofGateProof`) | `CredentialOperationOutput` | Mint and selectively disclose credentials |
| `EligibilityProgram` | [src/eligibility/eligibility-program.ts](src/eligibility/eligibility-program.ts) | No | `EligibilityOutput` | Prove an eligibility credential is valid against a benefit plan |
| `AccessControlProgram` | [src/access-control/access-control-program.ts](src/access-control/access-control-program.ts) | No | `AccessControlOutput` | Prove a drug is on the formulary and within quantity limits |
| `PrescriptionProgram` | [src/prescription/prescription-program.ts](src/prescription/prescription-program.ts) | No | `PrescriptionOutput` | Prove a valid prescription status transition or pharmacy transfer |
| `FulfillmentProgram` | [src/fulfillment/fulfillment-program.ts](src/fulfillment/fulfillment-program.ts) | No | `FulfillmentOutput` | Settle a claim with in-circuit copay (no accumulator) |
| `AccumulatorFulfillmentProgram` | [src/fulfillment/accumulator-fulfillment-program.ts](src/fulfillment/accumulator-fulfillment-program.ts) | No | `AccumulatorFulfillmentOutput` | Settle a claim with deductible, OOPM, and benefit-max logic |
| `MessagingProgram` | [src/messaging/messaging-program.ts](src/messaging/messaging-program.ts) | No | `MessagingOutput` | Prove a message or delegation is well-formed |
| `PcpVerificationProgram` | [src/eligibility/pcp-verification-program.ts](src/eligibility/pcp-verification-program.ts) | No | `PcpVerificationOutput` | Prove a primary-care provider assignment |
| `WalletMigrationProgram` | [src/wallets/wallet-migration-program.ts](src/wallets/wallet-migration-program.ts) | No | `WalletMigrationOutput` | Prove identity continuity across enrollment keys (NFC recovery) |
| `BatchProgram` | [src/l2/batch-program.ts](src/l2/batch-program.ts) | Yes (`SelfProof`) | `BatchOutput` | Recursively fold many state-transition proofs |
| `ChainProgram` | [src/l2/chain-program.ts](src/l2/chain-program.ts) | Yes (`SelfProof`) | `ChainOutput` | Chain batches over time into a single chain proof |

Two structural rules govern every program in this list:

1. **A proof's public output is its only externally visible contract.** Private inputs (the witness) are invisible. The output Struct is what downstream consumers (other ZkPrograms, the on-chain CareContract, offline verifiers) bind their logic to.
2. **Recursion depth is capped at two.** No single proof verifies more than two other proofs, and no proof tree is deeper than two levels of nested verification. The reason is in [§ 10](#10-the-pickles-two-recursion-constraint).

## 5. Wallet ownership: ProofGateProgram

The base of the proof stack. A `ProofGateProof` says: *"I know a preimage that, hashed with the right domain tag, produces this walletId."*

```ts
export const ProofGateProgram = ZkProgram({
  name: 'ProofGate',
  publicInput: Field,        // walletIdentity
  methods: {
    verifyMember:    { privateInputs: [Field, Field, Field, Field, Field, Field], ... },
    verifyPrescriber:{ privateInputs: [Field, Field, Field], ... },
    verifyPharmacy:  { privateInputs: [Field, Field, Field], ... },
    verifyRepresentative: { privateInputs: [Field, Field, Field], ... },
  },
});
```

Each method recomputes the Poseidon hash from the preimage fields and asserts equality with the public `walletIdentity`. From [src/wallets/proof-gate.ts:69](src/wallets/proof-gate.ts#L69):

```ts
const computed = Poseidon.hash([
  DOMAIN_TAG_MEMBER,
  cardholderIdHash, dateOfBirth, firstNameHash, lastNameHash,
  enrollmentKeyHash, groupIdHash,
]);
computed.assertEquals(walletIdentity);
```

That is the entire circuit. A handful of Poseidon hashes and one equality assertion. The output is the `walletIdentity` itself. Anyone receiving this proof can verify offline (NFC, RFID, QR) that the bearer controls the wallet, without seeing any of the underlying identity data.

`ProofGateProgram` is used standalone for point-of-care identity attestation, and it is verified recursively by `CredentialProgram` for credential mint operations. Note that `StateTransitionProgram` *does not* recursively verify a `ProofGateProof`. It re-implements the same hash check inline. The reason is in [§ 10](#10-the-pickles-two-recursion-constraint).

## 6. State transitions: StateTransitionProgram

The core sequencer-facing proof. A `StateTransitionProof` says: *"Here is a valid transition from this old (registry, lifecycle) state to this new (registry, lifecycle) state, signed by someone who knows the wallet preimage."*

```ts
export class TransitionOutput extends Struct({
  walletId: Field,
  oldRegistryRoot: Field,
  newRegistryRoot: Field,
  oldLifecycleRoot: Field,
  newLifecycleRoot: Field,
}) {}
```

Two methods, both in [src/engine/state-transition.ts](src/engine/state-transition.ts):

- **`proveRegistration`** inserts a new wallet into the registry tree and sets its lifecycle to `REGISTERED`. The new commitment is `Poseidon.hash([walletId, EMPTY_CREDENTIAL_ROOT, Field(0)])` (initial nonce zero).
- **`proveWalletUpdate`** updates a wallet's credential inventory root and increments the nonce. It also asserts the wallet is not `REVOKED`.

### Why wallet ownership is inlined

Both methods take the seven-field padded preimage `[domainTag, f0, f1, f2, f3, f4, f5]` as private inputs and compute the `walletId` *inside* the circuit using `Provable.switch`:

```ts
function computeWalletId(domainTag, f0, f1, f2, f3, f4, f5) {
  const memberHash     = Poseidon.hash([DOMAIN_TAG_MEMBER, f0, f1, f2, f3, f4, f5]);
  const prescriberHash = Poseidon.hash([DOMAIN_TAG_PRESCRIBER, f0, f1, f2]);
  const pharmacyHash   = Poseidon.hash([DOMAIN_TAG_PHARMACY, f0, f1, f2]);

  const isMember     = domainTag.equals(DOMAIN_TAG_MEMBER);
  const isPrescriber = domainTag.equals(DOMAIN_TAG_PRESCRIBER);
  const isPharmacy   = domainTag.equals(DOMAIN_TAG_PHARMACY);
  isMember.or(isPrescriber).or(isPharmacy).assertTrue('Invalid domain tag');

  return Provable.switch([isMember, isPrescriber, isPharmacy], Field,
                         [memberHash, prescriberHash, pharmacyHash]);
}
```

This is the equivalent of a `ProofGateProgram.verifyX` call, but inlined as raw constraints instead of a recursive proof verification. The reason it has to be inlined is the recursion limit explained in [§ 10](#10-the-pickles-two-recursion-constraint). If wallet ownership were verified recursively here, the resulting `StateTransitionProof` would already sit at recursion depth 1, and the downstream `BatchProgram` (which verifies two `StateTransitionProof`s) would push past the safe limit and fail in the Pickles wrap step.

The cost of inlining is a few hundred extra constraints in the `StateTransitionProgram` circuit. The benefit is that the resulting proof is at recursion depth 0 and can be folded into a batch at depth 1.

After computing `walletId`, the method then performs the actual state mutation: it asserts the old leaves match (via `MerkleWitness.calculateRoot`), computes the new leaves, and emits the old and new roots in the `TransitionOutput`. This output is what the L1 `CareContract.settleTransition` method checks against on-chain state.

## 7. Credential operations: CredentialProgram

A different recursive path is taken by `CredentialProgram`, which *does* recursively verify a `ProofGateProof`. From [src/credentials/credential-program.ts:62](src/credentials/credential-program.ts#L62):

```ts
proveMint: {
  privateInputs: [ProofGateProof, CredentialData, CredentialInventoryWitness, Field],
  async method(ownershipProof, credentialData, inventoryWitness, oldInventoryRoot) {
    ownershipProof.verify();
    const walletId = ownershipProof.publicInput;
    ...
  },
}
```

This is fine here because `CredentialProgram` outputs are not folded into the recursive `BatchProgram` chain. They are consumed at the point of credential issuance, then committed via a different path (`CareContract.registerGlobalCredential`). The recursion budget of two only matters along the StateTransition -> Batch -> Chain hot path.

The three methods are:

- **`proveMint`**: prove a credential was correctly inserted into the wallet's inventory tree.
- **`proveHolding`**: prove the wallet still holds a specific credential. Used at point-of-care.
- **`proveHoldingByType`**: selective disclosure. Prove "I hold a credential of type X" without revealing which credential.

## 8. The claim flow: five ZkPrograms in series

A pharmacy claim is settled by chaining proofs from five `ZkProgram`s. None of them are individually recursive against `SelfProof`. They each verify a slice of the claim and emit a public output that the next proof (or the sequencer's audit log) consumes.

### 8.1 EligibilityProgram

*"This credential contains valid eligibility data against a real benefit plan."*

From [src/eligibility/eligibility-program.ts](src/eligibility/eligibility-program.ts), the `proveEligibility` method checks:

1. Credential type is `ELIGIBILITY` and not revoked.
2. Credential has not expired (`currentDate <= credentialData.expiresAt`, or `expiresAt == 0` for no expiry).
3. The six tree roots inside the credential's `ForestRoots` Struct hash to the credential's embedded `forestRoot` (forest integrity).
4. The `EligibilityData` leaf is present in the credential's `ACCESS_CONTROL` tree (Merkle witness).
5. The benefit plan referenced by the eligibility data exists in the insurer's on-chain `benefitPlanRoot`.
6. The current date is within the effective and termination dates.

### 8.2 AccessControlProgram

*"This drug is on the formulary, this quantity is allowed, and this prior auth (if required) is valid."*

Two methods in [src/access-control/access-control-program.ts](src/access-control/access-control-program.ts):

- **`proveFormularyAccess`**: NDC hash matches a `FormularyEntry` in the formulary tree, `requestedQuantity <= maxQuantityPerFill`, `requestedDaySupply <= maxDaySupply`, currentDate within validity.
- **`provePriorAuth`**: a `PriorAuthData` leaf with the right NDC and date range exists in the credential's `ACCESS_CONTROL` tree.

The output carries the medication's `tierLevel`, `copayAmount`, and `priorAuthRequired` flag, all derived from the formulary entry rather than from any out-of-band party.

### 8.3 PrescriptionProgram

*"This prescription validly transitioned from one status to another, or was transferred from one pharmacy to another."*

Two methods in [src/prescription/prescription-program.ts](src/prescription/prescription-program.ts):

- **`proveStatusUpdate`** asserts the prior status is in the `TRANSACTION` tree, the new slot is empty, the transition is valid per the state machine, and the new status links to the correct prescription.
- **`proveTransfer`** is the same but for a pharmacy-to-pharmacy transfer, with an additional check that the destination pharmacy matches the transfer authorization.

Pharmacy and prescriber wallet identities are verified inline (the H2 / M4 fix pattern: re-compute the wallet hash from `qualifier + idHash + enrollmentKeyHash` and assert equality with the bound wallet).

### 8.4 FulfillmentProgram

The first program that *does* something financial. From [src/fulfillment/fulfillment-program.ts:228](src/fulfillment/fulfillment-program.ts#L228):

```ts
const total = fulfillmentData.ingredientCostCents.add(fulfillmentData.dispensingFeeCents);
const copay = formularyEntry.copayAmountCents;
const totalLessThanCopay = total.lessThan(copay);
const patientPay = Provable.if(totalLessThanCopay, total, copay);
const planPay   = Provable.if(totalLessThanCopay, Field(0), total.sub(copay));
```

This is in-circuit adjudication. The pharmacy's pricing data and the formulary's copay rule meet inside the same proof, and the financial split is computed deterministically. No outside party gets to choose the amounts. The settlement commitment that gets written into the `TRANSACTION` tree is:

```ts
const settlementCommitment = Poseidon.hash([
  fulfillmentData.commitment(),
  patientPay,
  planPay,
]);
```

The new `TRANSACTION` tree root is computed from this commitment via the empty-slot witness, and the new forest root is computed from the six tree roots. The output exposes `patientPayCents`, `planPayCents`, `operationType` (claim or reversal), and `ndcHash`.

### 8.5 AccumulatorFulfillmentProgram

The production claim circuit. Same shape as `FulfillmentProgram` but reads the member's eligibility credential too and applies four-priority accumulator-aware logic. From [src/fulfillment/accumulator-fulfillment-program.ts:264](src/fulfillment/accumulator-fulfillment-program.ts#L264):

The priority order, outermost (highest) to innermost (lowest):

1. **OOPM met or mid-claim cap.** If the member's out-of-pocket maximum has been hit (or would be hit by this claim), patient pay is capped at remaining OOPM. ACA requirement.
2. **Annual benefit max exhausted or mid-claim cap.** If the plan's annual benefit is at or past its limit, plan pay is capped at remaining benefit and the patient picks up the rest.
3. **Deductible phase.** If the member has not yet met the deductible, patient pays `min(total, remainingDeductible)` plus a `copay` on any excess. This is the C5 fix in the source: a claim that straddles the deductible boundary is split correctly into a deductible portion and a copay portion on the post-deductible remainder.
4. **Normal.** Patient pays `min(total, copay)`, plan pays the rest.

The circuit then updates the accumulator (`deductiblePaidCents`, `oopPaidCents`, `annualBenefitUsedCents`) and emits a new eligibility-credential forest root. Both forest roots (the prescription credential's new root and the eligibility credential's new root) flow through the public output:

```ts
patientPayCents, planPayCents, deductibleCreditCents,
newForestRoot,                  // for the prescription credential
newEligibilityForestRoot,       // for the eligibility credential
```

A separate `proveReversalWithAccumulator` method reverses a settled claim, with **safe subtraction**: `Provable.if(deductiblePaidCents >= originalDeductibleCredit, sub, Field(0))`. Without the clamp, an underflow would wrap modulo the field prime and create huge accumulator values.

This program is the most constraint-heavy in the system but it is still at recursion depth 0. The sequencer treats its `FulfillmentOutput` as input to the audit chain, separate from the `StateTransitionProgram` -> `BatchProgram` -> `ChainProgram` settlement path.

## 9. Messaging, delegation, recovery

Three remaining programs handle ancillary flows. All three are recursion depth 0.

**`MessagingProgram`** (`proveSendMessage`, `proveDelegate`): proves a message or a delegation (representative appointment, AOR) is well-formed and committed to the messaging registry. Identity is verified separately by `ProofGateProgram` before the admin commits the message on-chain.

**`PcpVerificationProgram`**: proves a primary-care-provider assignment is bound to a real eligibility credential.

**`WalletMigrationProgram`**: proves identity continuity between an old wallet (with old enrollment key) and a new wallet (with new enrollment key). Used by the NFC recovery card flow when a member loses a device. Both 6-field preimages are private inputs. The circuit asserts the identity fields match while the enrollment keys differ, then outputs `{domainTag, oldWalletId, newWalletId}`. The sequencer then runs `EnrollmentService.processMigration` to terminate the old wallet, enroll the new one, and reconstruct the accumulator from `ClaimAccumulatorService` so the deductible-paid balance carries over.

## 10. The Pickles two-recursion constraint

Pickles is Mina's recursion layer over Kimchi. A `ZkProgram` method declares `maxProofsVerified` (implicit, derived from how many proof types appear in `privateInputs`), with a hard ceiling of 2. Beyond that, the system has a known bug ([o1js issue #1939](https://github.com/o1-labs/o1js/issues)) in `wrap_main.ml` where dummy proofs at recursion depth 2+ crash the prover.

The practical consequence is that any proof chain of the form `A -> B -> C -> D` will fail at C or D. Every chain in zpk.care is therefore at most two levels deep:

```
StateTransitionProof  (depth 0, wallet ownership inlined)
        |
        v
BatchProof            (depth 1, recursively wraps 1 or 2 StateTransitionProofs)
        |
        v
ChainProof            (depth 1 of its own chain, recursively wraps prev ChainProof + BatchProof)
        |
        v
CareContract.settleBatch (verifies BatchProof on L1)
```

The wallet-ownership inline trick in `StateTransitionProgram` (see [§ 6](#6-state-transitions-statetransitionprogram)) exists exactly because the alternative, `ProofGateProof -> StateTransitionProof -> BatchProof`, would already be at depth 2 inside `BatchProgram` and a `mergeBatches` call would push it to depth 3.

The same constraint shapes `BatchProgram`'s uniform-pair design (see [§ 11](#11-recursive-batch-settlement-batchprogram)). Heterogeneous methods (some taking one proof, some taking two) trigger the dummy-proof crash, so every method takes exactly two proof inputs of the same type.

These are not nice-to-have engineering decisions. They are forced moves. The proof graph is shaped this way because the prover otherwise crashes.

## 11. Recursive batch settlement: BatchProgram

From [src/l2/batch-program.ts](src/l2/batch-program.ts). Three methods, all with exactly two `StateTransitionProof` or `SelfProof` inputs:

```ts
wrapSingle:    [StateTransitionProof, StateTransitionProof]  // pass same proof twice (padding)
wrapPair:      [StateTransitionProof, StateTransitionProof]  // two sequential transitions
mergeBatches:  [SelfProof, SelfProof]                        // two BatchProofs
```

`wrapSingle` is the base case for an odd transition count: the second proof is verified but its output is discarded. `wrapPair` is the normal base case for two sequential transitions, with **chain enforcement** between them:

```ts
left.newRegistryRoot.assertEquals(right.oldRegistryRoot, '... chain broken ...');
left.newLifecycleRoot.assertEquals(right.oldLifecycleRoot, '... chain broken ...');
```

`mergeBatches` recursively combines two `BatchProof`s with the same chain enforcement. The structure is a **balanced binary tree of pair-wraps and merges**:

```
N transitions:
   pair-wrap N/2 times  (log2 width)
   merge log2(N/2) times
```

For four transitions: two `wrapPair` calls then one `mergeBatches`, three operations total. The output `BatchOutput` carries `oldRegistryRoot`, `newRegistryRoot`, `oldLifecycleRoot`, `newLifecycleRoot`, `registrationCount` (how many of the N transitions were wallet registrations), and `transitionCount`.

The reason for the uniform-pair pattern is the same as everything else in this section: heterogeneous arities trigger the Pickles dummy-proof bug. Every method takes exactly two proofs of one type.

## 12. The chain: ChainProgram and GlobalState

The L2 sequencer produces one batch per interval. Batches are chained over time into a `ChainProof`. The chain proof certifies the entire history of the system as a single Pickles proof of about 22 KB.

From [src/l2/chain-program.ts](src/l2/chain-program.ts):

```ts
ChainProgram = ZkProgram({
  name: 'ChainProof',
  publicOutput: ChainOutput,    // 5 Fields
  methods: {
    genesis:  { privateInputs: [BatchProof, Field, Field, Field, Field, Field, Field], ... },
    advance:  { privateInputs: [SelfProof, BatchProof, Field, Field, Field, Field, Field, Field], ... },
  },
});
```

`genesis` is the first block. `advance` proves block N from block N-1 plus a new batch, enforcing continuity:

```ts
batch.oldRegistryRoot.assertEquals(prev.registryRoot,  'Chain break: batch.oldRegistryRoot != prev.registryRoot');
batch.oldLifecycleRoot.assertEquals(prev.lifecycleRoot, 'Chain break: batch.oldLifecycleRoot != prev.lifecycleRoot');
```

Both methods compute a **global state root** from ten Fields. Per [src/l2/global-state.ts](src/l2/global-state.ts):

```
GlobalState (10 Fields, canonical ordering):
  0  walletRegistryRoot      wallet registry Merkle root
  1  walletCount             total registered wallets
  2  adminPublicKeyHash      Poseidon hash of admin public key
  3  lifecycleRoot           lifecycle tree Merkle root
  4  benefitPlanRoot         benefit plan registry root
  5  credentialRegistryRoot  credential registry Merkle root
  6  eligibilityVkHash       eligibility verification key hash
  7  messagingRoot           messaging composite root
  8  auditChainHash          Poseidon hash chain head
  9  blockHeight             L2 block number

globalStateRoot = Poseidon.hash(above)
```

Six of these (slots 2, 4, 5, 6, 7, 8) come into the chain program as private inputs because they live in the admin's `AdminStateConfig`. They are committed into `globalStateRoot`, so any tampering produces a root that does not match downstream chain proofs.

The `ChainOutput` exposes only five Fields:

```ts
class ChainOutput extends Struct({
  globalStateRoot: Field,
  blockHeight: Field,
  registryRoot: Field,
  lifecycleRoot: Field,
  walletCount: Field,
}) {}
```

`registryRoot` and `lifecycleRoot` are exposed explicitly because the next block's `BatchProof.oldRegistryRoot` must equal `prev.registryRoot`, and Poseidon is not invertible inside a circuit. The other fields collapse into `globalStateRoot`.

A node holding nothing but the latest `ChainProof` (about 22 KB) can verify the entire history without storing any transaction data.

## 13. State model: every Merkle commitment

The sequencer maintains a small fleet of Merkle-committed structures. Every height and leaf format below is from the actual source.

### Wallet registry and lifecycle

| Tree | Height | Capacity | Leaf | File |
|---|---|---|---|---|
| Wallet registry | 11 | 1,024 wallets | `Poseidon.hash([walletId, credentialInventoryRoot, nonce])` | [src/wallets/wallet-state.ts](src/wallets/wallet-state.ts) |
| Lifecycle | 11 | 1,024 entries | `Poseidon.hash([walletId, lifecycleState])` | [src/engine/lifecycle.ts](src/engine/lifecycle.ts) |

Lifecycle is the per-wallet state machine `EMPTY(0) -> REGISTERED(1) -> ELIGIBLE(2) -> ACTIVE(3) -> REVOKED(4)` with admin-only revoke shortcuts from `REGISTERED` and `ELIGIBLE`. The transition validity is enforced inside a circuit by `assertValidTransition` (six OR'd cases). The leaf binds the lifecycle value to `walletId`, so observing the tree reveals no usable per-wallet information without already knowing the wallet ID.

### MerkleForest (per credential)

Six domain-specific trees, all height 8 (128 leaves each), composed into a single `forestRoot`. Defined in [src/zkp/merkle-forest.ts](src/zkp/merkle-forest.ts):

```ts
forestRoot = Poseidon.hash([
  memberRoot, prescriberRoot, pharmacyRoot,
  medicationRoot, accessControlRoot, transactionRoot,
])
```

The trees serve different purposes:

| Tree | Use |
|---|---|
| MEMBER | Member identity entries inside the credential |
| PRESCRIBER | Prescriber identity entries |
| PHARMACY | Pharmacy identity entries |
| MEDICATION | Prescription records (Rx data, NDC, sig) |
| ACCESS_CONTROL | Slot 0 holds `EligibilityData`, slots 1-126 hold `PriorAuthData`, slot 127 holds `AccumulatorData` |
| TRANSACTION | Append-only ledger of status updates and fulfillment settlements |

The forest is itself a leaf into the wallet registry: a wallet's `credentialInventoryRoot` (height 7, 64 credentials per wallet) holds credential commitments, each of which references a `forestRoot`.

### Claim accumulator (sequencer-side)

From [src/l2/claim-accumulator-service.ts](src/l2/claim-accumulator-service.ts):

| Tree | Height | Capacity | Leaf |
|---|---|---|---|
| Claim accumulator | 24 | ~8,388,608 leaves (2^23) | 9-Field `Poseidon.hash` |

The leaf format:

```ts
ClaimLeaf = Poseidon.hash([
  memberWalletId, ndcHash, pharmacyWalletId, prescriberWalletId,
  dateOfService, patientPayCents, planPayCents, operationType, deductibleCreditCents,
])
```

The service maintains four side indexes (`memberIndex`, `pharmacyIndex`, `prescriberIndex`, `ndcIndex`, each `Map<string, bigint[]>`) for O(1) lookups, plus a `fillDedup` map keyed by `member:ndc:pharmacy:dateOfService` to prevent duplicate dispensing. The Merkle root snapshot is recorded on every `L2Batch` and persists across checkpoints.

### Other sequencer-side trees

| Service | Tree | Height | Capacity |
|---|---|---|---|
| `MessageStoreService` | Encrypted message store | 20 | ~524,288 messages (2^19) |
| `ProviderRegistryService` | Credentialed providers | 16 | 32,768 |
| `FormularyRegistry` | Drug list | 16 | 32,768 entries |
| `BenefitPlanRegistry` | Plan definitions | 8 | 128 plans |

The message store stores ciphertext + IV + tag only. No plaintext touches the sequencer. The recovery flow is documented in [§ 9](#9-messaging-delegation-recovery).

## 14. Audit hash chain

Every state-changing event is appended to a Poseidon hash chain that serves as the data-availability layer. From [src/audit/audit-service.ts:64](src/audit/audit-service.ts#L64):

```ts
eventCommitment = Poseidon.hash([
  walletId, oldRegistryRoot, newRegistryRoot,
  oldLifecycleRoot, newLifecycleRoot, sequenceNumber, isRegistration,
  ndcHash, patientPayCents, planPayCents,
])

chainHash = Poseidon.hash([prevChainHash, eventCommitment])
```

Non-claim events use zero for `ndcHash`, `patientPayCents`, and `planPayCents`. Genesis hash is `Poseidon.hash([Field(0)])`. The current chain head is field 8 of the `GlobalState` commitment, so any tampering would produce a root that disagrees with the chain proof.

`AuditService` is stateless. It takes audit log records as input and verifies:

1. **Chain integrity**: recomputed `chainHash` matches the recorded one at every event.
2. **Financial balance**: `patientPayCents + planPayCents == ingredientCostCents + dispensingFeeCents` for every claim.
3. **Duplicate detection**: no two events with the same `member:ndc:pharmacy:dateOfService` are both `operationType=1` (claim, not reversal).
4. **Sequence gaps**: monotonic `sequenceNumber` per wallet.
5. **L1 settlement**: the on-chain roots after each batch match the batch's `BatchOutput`.

The chain hash is the auditor's anchor. Given it, every event commitment can be independently recomputed from public claim data and checked.

## 15. The Leviathan trust layer

The Leviathan is the partitioned, multi-leader sequencer network that replaces an L1 blockchain. From [src/l2/l2-leviathan.ts](src/l2/l2-leviathan.ts):

- N **partition sequencers** (each an `L2SequencerService` with its own root chain).
- One leviathan instance leads its primary partition and replicates all others by gossip.
- A 5-second heartbeat plus a 15-second failover timeout triggers deterministic promotion if a leader is silent. The failover chain is fixed up-front and the highest-priority surviving node wins, preventing split-brain.
- The shared `L2PeerNetwork` epidemic-broadcasts a `GossipMessageType` union of 16 distinct messages (defined in [src/l2/l2-peer-types.ts:79](src/l2/l2-peer-types.ts#L79)): six core (`proof:accepted`, `batch:built`, `batch:settled`, `batch:failed`, `state:snapshot`, `peer:announce`), one for messaging (`message:stored`), three for plan/formulary replication (`plan:updated`, `plan:deleted`, `formulary:updated`), two for leader management (`leader:heartbeat`, `leader:promotion`), three directed quorum messages (`quorum:propose`, `quorum:vote`, `quorum:certificate`), and one admin (`admin:eviction`). Deduplication uses a bounded `Set` (max 10K entries with half-eviction).
- Reads aggregate across partitions; writes route to the correct partition's leader by hashing the wallet ID with `PartitionRouter`.

The leviathan is the trust layer in a precise sense: there is no L1 blockchain settling proofs. Finality is established when N/2+1 leviathans have logged and signed the proof (see [§ 16](#16-durability-wal-quorum-state-certificates)). The chain proof at the head of the system is the historical anchor.

## 16. Durability: WAL, quorum, state certificates

Two mechanisms work together to give zero-data-loss guarantees on a system that does not settle to an L1.

### Write-ahead log

From [src/l2/l2-wal.ts](src/l2/l2-wal.ts). Per-partition append-only NDJSON log with `fsync` before any in-memory mutation. Eight entry types: `proof`, `batch_begin`, `batch_commit`, `batch_abort`, `settle`, `fail`, `plan_store`, `plan_delete`.

Every entry includes:

```ts
{
  entryId,            // SHA-256
  sequenceNumber,     // monotonic per partition
  type,
  partitionIndex,
  ...payload,         // proof JSON, receipt data, audit event, etc.
  integrityHash,      // HMAC-SHA-256 chained from prev entry
  prevIntegrityHash,
  timestamp,
  committed,          // false until corresponding commit marker is written
  originNodeId,
}
```

Commit markers are separate WAL lines. On crash recovery, any uncommitted entry is replayed: the proof is re-verified, the receipt is re-emitted, the audit event is re-appended. The HMAC chain detects any line tampering or partial writes.

### Quorum writes

From [src/l2/l2-quorum-service.ts](src/l2/l2-quorum-service.ts). A leader does not unilaterally accept a proof. The flow is:

1. Leader writes the proof to its own WAL (uncommitted).
2. Leader broadcasts a `QuorumProposal` (gossip type `quorum:propose`) carrying the proof and the proposed WAL entry.
3. Each peer verifies the proof, writes its own WAL entry, signs an Ed25519 `QuorumVote` over the canonical vote message, and replies (`quorum:vote`, directed).
4. The leader collects votes. Once N/2+1 (including its own) have been received within `DEFAULT_QUORUM_TIMEOUT_MS` (default 5 seconds), it assembles a `QuorumCertificate` containing all signatures, writes a commit marker to its WAL, mutates in-memory state, emits the receipt to clients, and gossips the certificate (`quorum:certificate`).

The receipt that clients see therefore carries a quorum certificate proving that N/2+1 leviathans have committed it. A subsequent batch boundary triggers a **state certificate**: each leviathan signs the batch's state digest (`computeStateDigestHash`) and the signatures are aggregated. The state certificate is attached to the `L2Batch`. The signer public keys are checked against the registered peer registry, not the keys embedded in the certificate. Embedded-key trust is the classic "self-attestation" mistake; the security hardening done on 2026-04-17 introduced the peer-registry cross-check.

### Checkpoint and recovery

State is checkpointed atomically (`temp -> fsync -> rename`), after which the WAL is compacted past the checkpoint cursor. Recovery is `loadCheckpoint -> replayUncommittedWal -> ready`.

`L2Leviathan.fromCheckpoint()` reconstructs the entire leviathan (per-partition states, leader map, failover chain) from a `LeviathanCheckpoint`. Crash-tested in `tests/l2-leviathan.test.ts`.

## 17. The proving pool

o1js's Pickles / Kimchi prover is **single-threaded per process**. There is a global `_provingLockQueue` mutex that serializes every proof call. Three concurrent proofs in one process queue. Six concurrent proofs stall.

The fix, from [src/l2/l2-proving-pool.ts](src/l2/l2-proving-pool.ts) and [src/l2/l2-proving-worker.ts](src/l2/l2-proving-worker.ts): a pool of N child processes, each with its own o1js context, each holding the full circuit verification key in memory after a one-time compile.

```ts
const pool = new ProvingPool(3);   // 3 workers
await pool.start();                // each worker compiles independently
const result = await pool.prove(job);  // dispatched to first idle worker
await pool.shutdown();
```

The coordinator and workers speak a small IPC protocol over `child_process.fork()`:

| Coordinator -> worker | Worker -> coordinator |
|---|---|
| `compile` (with program registry) | `ready` |
| `prove` (job request, args serialized) | `result` (proof JSON) or `error` |
| `shutdown` | (graceful exit) |

All `Field` values cross the boundary as decimal strings; proofs cross as `toJSON()` / `fromJSON()` payloads. The sequencer's `buildBatch` is split into:

- `prepareBatch()` (main process): drain the pending pool, serialize the witness data.
- `pool.prove(job)` (worker): run `BatchProgram.wrapSingle` / `wrapPair` / `mergeBatches`, optionally followed by `ChainProgram.advance`, return the resulting proof JSON.
- `finalizeBatch(result)` (main process): write metadata, emit receipts, hand off to settlement.

Worker crashes are detected and the pool restarts the worker up to three times before failing the batch. Job timeouts default to 5 minutes per prove call.

The pool is optional. If unconfigured, the system falls back to the single-process proving lock and remains correct, just serial.

A privacy note: only Poseidon hashes and ZK proofs ever cross the worker boundary. No PHI is ever passed to the pool. The privacy invariant is preserved by construction because the inputs to a batch are already public `TransitionOutput`s and `BatchOutput`s.

## 18. End-to-end walkthrough

A real claim from enrollment to settlement, with the proof type at each step in brackets.

### Enrollment

1. **Employer** issues a `GroupEnrollmentToken` (8 Fields, all hashes) via the HR Tool. The token includes `familyIdHash` and is delivered with an out-of-band PIN. The employer node never sees plaintext employee identity; that lives on the HR workstation only, encrypted at rest with scrypt + AES-256-GCM.
2. **Member** on device:
   - Generates a 256-bit enrollment key with `generateEnrollmentKey()`.
   - Validates token + PIN locally.
   - Derives `walletId = Poseidon.hash([0, hash(cardholderId), hashDate(dob), hash(firstName), hash(lastName), hash(enrollmentKey), groupIdHash])`.
   - Builds the 7-field padded preimage `[domainTag, f0, f1, f2, f3, f4, f5]`.
   - Generates a `StateTransitionProof` via `StateTransitionProgram.proveRegistration`. **[Proof 1]**
3. **Insurer**: receives the walletId and proof, calls its sequencer to submit. The insurer never learns the member's name, DOB, or enrollment key.
4. **Sequencer**:
   - Verifies the proof.
   - Writes WAL entry (uncommitted).
   - Broadcasts `QuorumProposal`.
   - Collects N/2+1 Ed25519 votes, assembles `QuorumCertificate`.
   - Mutates wallet registry: insert wallet leaf at next index, lifecycle to `REGISTERED`.
   - Appends `AuditEvent` to Poseidon chain.
   - Emits `L2Receipt` with quorum certificate to client.
5. **Insurer mints credentials**:
   - Lifecycle: `REGISTERED` -> `ELIGIBLE` -> `ACTIVE`.
   - Issues an `ELIGIBILITY` credential containing the member's plan, deductible, OOPM, and benefit max. The accumulator data lives at leaf 127 of the credential's `ACCESS_CONTROL` tree.

### Prescription

1. **Prescriber** writes an e-prescription:
   - Builds `PrescriptionData` (member wallet, NDC, dose, quantity, daysSupply).
   - Generates `PrescriptionProgram.proveStatusUpdate` to advance from `EMPTY` to `PENDING`. **[Proof 2]**
   - Submits to its node, which forwards to the sequencer.
2. The Rx credential lands in the member's credential inventory (separate flow via `CredentialProgram.proveMint`). **[Proof 3]**

### Fulfillment

1. **Pharmacy** scans the member's NFC card or wallet QR:
   - Reads an `NfcCredentialAttestation` (Ed25519-signed compact credential, ~578 bytes, fits NTAG216's 888-byte payload). Verifies the signature against the registered sequencer public key.
   - Confirms expiry has not passed.
2. Pharmacy clinical system computes the claim:
   - `FulfillmentData` with `ingredientCostCents`, `dispensingFeeCents`, `quantityDispensed`, `pharmacyWalletId`, `prescriptionHash`.
3. Pharmacy generates `AccumulatorFulfillmentProgram.proveFulfillmentWithAccumulator`:
   - Private inputs: prescription credential, prescription data, latest status, fulfillment data, formulary entry, both `ForestRoots` Structs, four `ForestMerkleWitness`es, one `FormularyMerkleWitness`, formulary root, the accumulator, the accumulator witness, and the pharmacy preimage triple.
   - Circuit runs the four-priority adjudication logic and computes `patientPay`, `planPay`, `deductibleCredit`.
   - Computes the settlement commitment `Poseidon.hash([fulfillmentData.commitment(), patientPay, planPay, deductibleCredit])`.
   - Updates the accumulator inside the circuit and computes the new eligibility forest root.
   - Emits `AccumulatorFulfillmentOutput`. **[Proof 4]**
4. Pharmacy also generates `StateTransitionProgram.proveWalletUpdate` to commit the new credential roots to the sequencer. **[Proof 5]**
5. The pair of proofs goes to the sequencer.

### Sequencer side

1. **Verify** each proof.
2. **WAL + quorum**:
   - Write `proof` WAL entry, broadcast proposal, collect votes, write commit marker.
3. **Audit chain**:
   - Append `AuditEvent` with `ndcHash`, `patientPayCents`, `planPayCents` set.
   - Update chain head.
4. **Claim accumulator**:
   - `ClaimAccumulatorService.append` adds a `ClaimLeaf` and updates the four indexes plus the dedup map.
5. **L2Receipt**:
   - Returned to pharmacy with `quorumCertificate`, `claimLeafIndex`, batch metadata.
6. **At batch boundary** (timer or pending threshold):
   - `prepareBatch()` drains pending transitions, serializes them.
   - `provingPool.prove({ program: 'BatchProgram', method: 'wrapPair' or 'wrapSingle', args })` runs in worker.
   - For N > 2 transitions, multiple `wrapPair` calls then `mergeBatches` in a balanced tree.
   - Optional `ChainProgram.advance` call composes the new batch onto the prior chain proof.
   - `finalizeBatch(result)` records the `L2Batch`, emits `batch:built` gossip, attaches a `StateCertificate` (N/2+1 Ed25519 signatures of the new state digest).
7. Replicas receive the batch + certificate via gossip and update their own state.

### Settlement

Finality is local: the moment a proof has its quorum certificate, the receipt is durable. There is no L1 round-trip for settlement in the default configuration. The chain proof at the head of the system is the historical anchor, and the audit chain plus the state certificates are the verifiability anchor.

### Offline path

The pharmacy flow above works without any internet at all up to the point of submission. Eligibility and formulary access can be verified entirely against the member's credential and an NFC-signed attestation. The settlement proof can be generated locally and queued. When the pharmacy reconnects, the proof submits and the receipt comes back. This is the offline mode the README references as "a tap of an NFC card."

## 19. Why this works

The recurring theme in this document is that the proof system is shaped by the constraints of the prover, not by what a clean-slate design would look like. Three specific choices are the difference between "this works" and "this crashes."

**1. Wallet ownership is inlined in `StateTransitionProgram`.** If it were recursive (via `ProofGateProof`), the `BatchProgram` that wraps two `StateTransitionProof`s would be at depth 2, and `mergeBatches` of two `BatchProof`s would push to depth 3. The Pickles `wrap_main.ml` bug would trigger. The cost of inlining is a few hundred extra constraints in `StateTransitionProgram`. The benefit is that everything downstream remains under the recursion cap.

**2. `BatchProgram` uses uniform-pair arity.** Every method takes exactly two proofs of the same type. `wrapSingle` accepts a "padding" duplicate. This avoids heterogeneous-arity proof verification in a single program, which triggers a different Pickles crash with dummy proofs at depth >= 2.

**3. Proving runs in child processes.** o1js's `_provingLockQueue` is process-global. Without a pool, concurrent batches at the sequencer serialize and stall under realistic load. The pool gives true CPU parallelism by buying one o1js context per worker.

The result is a proof graph that is small enough to compose without crashing, deep enough to amortize many transitions into one verification, and parallel enough to keep up with submission rate. Combined with the off-chain Leviathan trust layer (WAL plus quorum plus state certificates), it produces a system that:

- Adjudicates claims fully inside ZK circuits, so the financial split is tamper-evident.
- Never sees PHI on the network, because the wallet model derives addresses from hashed identity data plus a device-only key.
- Reaches finality without an L1 settlement layer, because N/2+1 Ed25519-signed quorum certificates give zero-data-loss durability.
- Verifies an arbitrary-length history from a 22 KB chain proof, because every block recursively certifies its predecessor.

When the design constraints, the proof framework, and the operational layer all line up at once, "trust us, we will be fair" stops being the security model. The proofs are the security model. The math is the policy. That is the thing this software is actually for.
